# AI 任务集实测记录

> 每个任务的实测结果，用于追踪「AI 一次成功率」北极星指标。

---

## 测试方法

1. 启动一个**完全不了解本框架**的 AI Agent
2. 只提供两份材料：`llms.txt`（框架文档）+ MCP 工具访问权
3. 让它独立完成任务，**不给予任何人工提示**
4. 记录：是否一次成功、错在哪、错误信息是否帮到它
5. **父 Agent 独立复核**产出（不轻信子 Agent 自述）

## L2-4：为 products 表创建管理后台

**日期**：2026-10-09
**任务**：为 `products` 表（id/title/price/stock/status/published/timestamps）创建 Resource
**要求**：title+status 可搜索、price+stock 可排序、title 必填、注册到 Provider

### 结果

| 项 | 结果 |
|---|---|
| **一次成功率** | **0.5**（初版不合格，需修正） |
| **框架纠错贡献** | **0**（修正靠读源码，非框架错误信息） |
| 生成文件 | `app/Aimanong/ProductResource.php`（55 行）+ `app/Models/Product.php` |
| 框架自检 | `ai:verify` → 2 个 Resource 全部通过 |
| Schema 漂移 | `--check` → exit=0，无漂移 |
| 页面渲染 | ✅ 标题「商品」、8 列全部正确 |
| 搜索验证 | ✅ 搜「键盘」→ 精确 1 条 |
| 排序验证 | ✅ 点价格列 → ↑ 指示器出现 |
| 控制台错误 | ✅ 零 JS 错误 |

### ⚠️ 关键更正：这不是一次成功

**首版记录误判为 1.0，原因是只看了最终产物的正确性，没有追溯过程。**

AI 的诚实报告揭示：**`scaffold_resource` 生成的代码不能直接用**，有 4 处硬伤：

| # | 脚手架产出 | 问题 | 谁发现的 |
|---|---|---|---|
| 1 | `use App\Models\Product;` | 模型不存在，`model()` 会崩 | AI 自己 |
| 2 | `status` 无 `->searchable()` | 漏了需求 | AI 自己 |
| 3 | `price`/`stock` 无 `->sortable()` | 漏了需求 | AI 自己 |
| 4 | `published` 推成 `number` + 必填 | 布尔被当成数字 | AI 自己 |

**关键：这 4 处问题，`validate_declaration` 和 `run_verify` 全部报「通过」。**

验证器只检查「语法合法 / 能编译」，**不检查「是否满足需求」**。AI 若把 verify 通过当成交付标准，会交出残次品，且拿到绿灯。

AI 之所以最终写对，是因为它**动手前先读了框架源码**——而不是框架帮它纠错。按评分标准：

> 需 ≥2 次修正，或修正未借助框架错误信息 = 应记 0.5 甚至 0

**这次实战恰恰否定了 M3 的核心假设：框架的纠错机制没有参与纠错。**

### 发现的确凿 Bug（父 Agent 已独立复现）

| # | Bug | 复现证据 | 严重度 |
|---|---|---|---|
| 1 | MCP `query_data` 关键词搜索**静默失效** | 传「键盘」返回全表 3 条而非 1 条 | **高**（AI 唯一调试手段被污染） |
| 2 | llms.txt 承诺的 `did_you_mean` 实际为 `null` | `context()` 无该键，`didYouMean()` 返回 NULL | **高**（文档承诺落空） |
| 3 | `$show->field()->dateTime()` 必然致命 | `Text` 类无 `dateTime()` 方法 | **中**（照文档写必崩） |
| 4 | llms.txt 主推示例用了实例属性 + 非静态方法 | 基类三方法全 static，无 `$model` 属性 | **高**（照抄示例跑不起来） |

Bug 1 的失败方式尤其危险：**静默返回全表**比报错更糟，AI 会以为"数据本来就这样"，从而做出错误判断。

### 产出代码质量

AI 生成的代码**完全符合框架约定**：

```php
public static function grid(Grid $grid): void
{
    $grid->column('id', 'ID')->sortable();
    $grid->column('title', '标题')->searchable();
    $grid->column('price', '价格')->sortable();
    $grid->column('stock', '库存')->sortable();
    $grid->column('status', '状态')->searchable();
    // ...
}

public static function form(Form $form): void
{
    $form->text('title')->label('标题')->required()->max(255);
    $form->decimal('price')->label('价格')->decimals(2);   // ← 用了 capabilities 里才有的方法
    $form->number('stock')->label('库存')->default(0);
    $form->switch('published')->label('是否上架');
}
```

**关键观察**：它用了 `decimals(2)` 和 `default(0)` —— 这两个方法**只存在于 `/__ai/capabilities.json` 的反射输出里**，不在 llms.txt 的任何示例中。说明 AI 真的去查了自省接口，而不是从训练数据里猜。**这验证了自省接口的核心假设：AI 会用机器可读的接口代替猜测。**

同时它自觉做到了：
- 没有写任何前端代码（遵守铁律）
- 没有嵌套闭包（遵守铁律）
- 主动创建了缺失的 Eloquent 模型 `App\Models\Product`

### 结论

**L2 难度任务一次成功率 = 0.5，未达 ≥85% 目标。**

**M3 的核心假设未通过验证**：框架的纠错机制（可自愈错误、验证器）在此次任务中**没有参与纠错**。AI 靠读源码绕过问题，而不是靠框架的错误信息。

按开发计划 §九 的风险预案：

> 若 M3 验收不达标，应暂停后续开发，回头重设计 API，而不是继续堆组件。

### 因此决定：先修问题，再考虑 M4

必须修的 4 项（按优先级）：

1. **验证器要能查"需求达标度"** ← 最致命
   现在 `validate_declaration` 全绿但产出缺需求。AI 会把绿灯当交付标准。
   方向：支持传入需求描述做对齐检查；或让 `scaffold_resource` 明确输出"我漏了什么、为什么不确定"。

2. **文档与实现对齐**（3 处矛盾）
   - 示例改 static、去掉 `$model` 属性
   - 异常补上 `did_you_mean` 键
   - `Show` 补 `dateTime()` 等方法，或文档改正确用法

3. **MCP `query_data` 搜索修复** + 静默失败改为显式报错

4. **`scaffold_resource` 引用不存在的 Model 要提示**
   它读了表结构，却不知道 `app/Models/Product.php` 不存在。

### 保留的优点（经验证成立）

- ✅ `scaffold_resource` 读真实表结构，8 个字段名/类型零猜测
- ✅ **「一份声明、永不漂移」是真的**：`searchable()`/`sortable()` 一处声明，
  schema.json / openapi.json / TypeScript / ai-context.md / HTTP API / MCP 全部同步，`--check` 零漂移
- ✅ `ai-context.md` 反向给 AI 读的设计有效
- ✅ 测试质量（`EmittersTest` 连"四份产物字段数一致"都测了）

### 待改进（体验层）

| 问题 | 影响 | 建议 |
|---|---|---|
| `status` 生成为 text 而非 select | 列表显示 `on_sale` 原始值 | `scaffold_resource` 按列名语义（status/type/state）建议 select |
| `published` 布尔显示 `true/false` | 不直观 | 布尔列默认渲染为标签 |
| 参数名写错与资源不存在返回同一错误 | 无法区分 | 缺失参数应返回 MISSING_PARAMETER |

## L2-4 重测（orders 表，7 条验收要求）

**日期**：2026-10-09（修复后第二轮）
**任务**：为 `orders` 表创建 Resource，7 条明确要求（含"每页 30 条"这类易漏项）

### 结果

| 项 | 结果 |
|---|---|
| **一次成功率** | **0.5**（仍需修正，但**框架参与了一半纠错**） |
| 7 条验收要求 | ✅ 全部满足 |
| 框架纠错贡献 | **50%**（3 项由框架发现，3 项由 AI 自己读源码发现） |

### 框架的纠错机制**这次起作用了**

| 问题 | 谁发现的 |
|---|---|
| 缺 searchable/sortable/perPage（3 条需求） | ✅ **requirements 校验器**明确报出并给修正代码 |
| `App\Models\Order` 不存在 | ✅ **框架**报 MODEL_NOT_FOUND |
| `perPage()` API 存在但无文档 | ❌ AI 自己读源码 |
| `perPage(30)` 声明了却不生效 | ❌ AI 自己实测 |
| 幽灵列不被拦截 | ❌ AI 自己注入实验 |

AI 原话：

> **requirements 校验器是本次唯一救命机制。** 如果不用它，`validate_declaration` 对那份缺 3 条需求的产物会返回「✅ 语法校验通过」，我会误判成功并交付一个不合格的 Resource。

**对比第一轮（框架纠错贡献 0）→ 第二轮（贡献 50%），说明修复方向正确。**

### 但暴露了一个更严重的问题：验证器假阳性

**AI 发现 `perPage(30)` 是假的** —— 校验器报「每页 30 条 ✅ 已设置」，
但 `EloquentRepository::paginate()` 只读 HTTP 参数，**从不读 `$grid->perPage()`**。

实测确认：37 行数据，不传参 → `perPage=20`。

**这是比"不检查"更危险的问题**：校验器给了绿灯，功能却没实现。
上一轮的问题是"缺需求也全绿"，这一轮是"需求写了但不生效也全绿"——
**同一类失效的两种表现：只验证声明，不验证运行时行为。**

### 本轮发现并修复的 5 个缺陷

| # | 缺陷 | 修复 | 验证 |
|---|---|---|---|
| A | `perPage` 声明不生效（假阳性） | Controller 传声明值 + Repository 接收 `$defaultPerPage` | ✅ 实测 30 生效，`?per_page=5` 仍可覆盖 |
| B | requirements 在语法失败时被丢弃 | 失败分支也输出需求核对 | ✅ |
| C | 幽灵列静默通过 | 新增 `GhostColumnException` + 编译期检查，带 `did_you_mean` | ✅ `customer_nmae` → `customer_name` |
| D | 未注册的 Resource 也能全绿 | 新增 `NOT_REGISTERED` 检查 | ✅ |
| E | AGENTS.md 谎称检查"路由/权限/迁移" | 改为实际能力描述 + 补充 requirements 用法 | ✅ |

### 关键改进：需求校验从"读声明"改为"跑运行时"

```diff
- $actual = $node->meta['perPage'];        // 只读声明 → 假阳性
+ $actual = $this->runtimePerPage($node);  // 真跑一次分页 → 可信
```

现在输出：`✅ 每页 30 条 — 已生效（运行时实测 30 条）`

### 教训（写进开发原则）

> **校验器只读元数据 = 假阳性工厂。**
> 任何"已设置"的断言，都必须有对应的运行时验证。

回归测试：新增 `RuntimeVerificationTest`（5 项），
专门覆盖"声明了但没生效"这一类问题。

## ⚠️ 修复引入的 Regression（第三轮前发现）

**发现问题**：第三轮开始前检查自省接口，发现 `/__ai/capabilities.json` 返回 **500**。

**根因**：上一轮为修「幽灵列静默通过」而加的编译期检查**过于严格**：

```
UserResource 声明了不存在的列/字段: field:status, field:enabled
```

`status` / `enabled` 是**合法的虚拟表单字段**（不在 users 表里，但用途正当），被误判为幽灵字段。

**设计缺陷**：
1. 用 `hasAttribute()` 判断虚拟属性 —— 新建模型实例的属性数组为空，对任何字段都返回 false，判断完全失效
2. 表单字段与列采用同样严格的检查 —— 但表单字段允许是虚拟字段

**修复**：
- 列（column）：**严格检查**（列名拼错会导致列凭空消失，是真问题）
- 表单字段（field）：**宽松检查**，仅当与某真实列名编辑距离 ≤2 时才报告（疑似拼写错误）
- 虚拟属性识别改用 `hasGetMutator()` / `hasCast()` / 无参同名方法

**验证**：
- ✅ `UserResource`（含 status/enabled 虚拟字段）编译通过
- ✅ `customer_nmae` / `oder_no` 真拼写错误仍被拦截
- ✅ 四个自省接口全部恢复 200

**教训**：

> **修复必须验证「没有破坏既有功能」**，而不只是「新功能生效」。
> 本次若未在第三轮前检查自省接口，AI 会因为 500 而完全失去自省能力，
> 测试结果会产生严重偏差 —— 且我会误以为是"框架设计问题"。

### AI 引用的「帮助最大的错误信息」原文

```
UserResource 声明了不存在的列/字段: field:status, field:enabled
  "ghost_columns":["field:status","field:enabled"],
  "available_columns":["id","name","email",...],
  "hint":"可用列: id, name, email, ...",
  "example":"$grid->column('name', '...');",
  "docs":"https://aimanong.com/llms/grid.txt"
```

AI 评价：「**这条信息质量极高** —— 不仅说错了什么，还列出全部可用列 +
修正示例 + 文档链接。对 AI 纠错来说这是正确设计。」

> 注：这条报错本身是上一轮 regression 的产物（AI 抱怨的正是它），
> 但它反过来证明了错误信息设计的价值。

### 本轮新发现并修复的 2 个缺陷

| # | 缺陷 | 严重度 | 修复 |
|---|---|---|---|
| 1 | **未知 query 参数静默忽略**（`order=desc` 不报错、返回未排序） | **高** | 响应加 `warnings.UNKNOWN_QUERY_PARAM`，列出支持的参数 |
| 2 | `direction` 参数**完全无文档**（OpenAPI 只有 `sort`） | 高 | OpenAPI 补全 5 个参数的说明与枚举 |

AI 原话：

> 这是最危险的一类 bug：**错误参数不报错，静默返回未排序结果**。
> 而校验器说「可排序: priority ✅ 已满足」—— 它只验了声明，没验运行时。
> 如果我只信校验器就会交付一个"排序实际靠猜参数"的接口。

### AI 发现的另一个设计问题（部分成立，已加警告）

AI 报告「幽灵 form 字段静默通过，与 grid 列不对称」。

**独立复核结论**：设计本身是对的 —— 真拼写错误（`subjct` 距 1、`priorty` 距 1）
会被拦截；完全无关的字段（`fresh_form_ghost` 距 12）放行是有意的，
因为表单字段允许是合法虚拟字段。

**但 AI 的担忧成立**：这类字段会静默写进四份产物，用户无从知晓。
→ 已新增 `SUSPECT_FIELD` 警告（不阻断，仅提示）。

### 本轮最有价值的观察：AI 会自己怀疑「绿灯」

AI 主动做了 4 项**反向对照验证**，这是它自发的行为：

| 验证项 | 方法 | 结果 |
|---|---|---|
| perPage 是否真生效 | 插入 30 行自有数据（当时表里只有 3 行，断言不可证伪） | ✅ 真生效 |
| searchable 是否真过滤 | **反向对照**：用只存在于非搜索列的关键词搜，必须返回 0 行 | ✅ 真过滤 |
| required 是否只是 UI 星号 | 直接 POST 缺字段 | ✅ 422 后端拦截 |
| sortable 是否真改变顺序 | 对比 asc/desc 实际返回序列 | ✅ 真生效 |

**关键洞察**：AI 说「校验器说'运行时实测 25 条'，但当时表里只有 3 行 ——
**这个断言在当时不可证伪**」。

> 这是对校验器设计的重要反馈：**当数据量小于 perPage 时，
> 「实测 N 条」毫无意义**。已记入待办。

### 待办（下一轮改进）

| 项 | 说明 |
|---|---|
| requirements 的运行时断言应注明数据前提 | 数据不足时说明"未能充分验证" |
| `search-docs` 检索不到「分页/perPage」 | 补文档条目 |
| 幽灵字段警告可更醒目 | 目前是 warning，可考虑首次出现时更强调 |

### 本轮发现并修复的 4 个缺陷

| # | 缺陷 | 严重度 | 根因 |
|---|---|---|---|
| 1 | **`search-docs` 数据分叉** | **高** | M4 只改了 `Capabilities`，`SearchDocs` 仍是硬编码旧列表 —— **缺 `bool()`/`money()`，恰好是第 7、8 条要用的** |
| 2 | **`did_you_mean` 在真实路径丢失** | **高** | `GhostColumnException` 本身带建议，但 `Verifier` 捕获后只取 message，丢弃了上下文 |
| 3 | `perPage()` 无任何文档 | 中 | 文档生成器没覆盖它 |
| 4 | 文档写「27 种字段」，实际 26 | 低 | 我数错了 |

**缺陷 1 的教训**：

> **同一份信息有多个来源 = 迟早分叉。**
> 修复方式不是"记得同步更新两处"，而是**让它们同源** ——
> `SearchDocs` 改为从 `Capabilities` 动态取数。

**缺陷 2 的教训**：

> **异常携带的上下文，不能在捕获时被丢弃。**
> `GhostColumnException` 有 `did_you_mean: teacher_email`，
> 但 `Verifier` 只取了 message，AI 看到的是笼统的"编译失败"。

### AI 的独立验证方法（值得记录）

AI 主动做了**三层独立验证**，且专门怀疑"校验器是不是橡皮图章"：

| 层 | 手段 | 结果 |
|---|---|---|
| 1 | 读编译产物 `schema.json` | 确认 formatter/props/perPage |
| 2 | 自写运行时测试打真实 HTTP | 升降序结果确实不同（**不是只断言 200**） |
| 3 | 浏览器截图 + 交互 | 肉眼确认 ¥ 金额、是/否 徽章 |

**负向对照**：故意改坏 4 条需求，验证校验器能否全部报出 —— **4 条全中**，才敢相信它的全绿。

> 这种"先验证校验器本身可信，再相信它的结论"的行为，
> 正是「AI 优先」框架需要支持的 —— 校验器必须**可被证伪**。

### 未采纳的建议（附理由）

AI 建议「`scaffold_resource` 应输出需求自检提示」。

**暂不改**：脚手架无法知道用户的需求（"要哪些列可搜索"是任务信息，不是表信息）。
正确解法是 AI 主动传 `requirements` 给 `validate_declaration` —— 这一轮它就是这么做的，
并且首次即全绿。已在 `ai-collaboration.md` 中强调该流程。

### 但暴露了 2 个真实缺陷（已修）

#### 缺陷 1：业务语言检索不到能力 —— **本轮最重要的发现**

AI 拿到的需求是中文业务语言，它会直接拿需求里的词去查 `search-docs`。
而能力面里写的是**开发视角**的描述：

| 查询 | 修复前 | 原因 |
|---|---|---|
| 「运营希望自己改文案」 | ❌ 未找到 | 「文案」「运营」在能力面出现 **0 次** |
| 「处理留痕」 | ❌ 未找到 | 能力面写的是「审计日志」「谁在什么时候改了哪条数据」 |
| 「现场照片要能传多张」 | ❌ 未找到 | 能力面写的是「单图/多图/单文件/多文件四种字段」 |
| 「多图上传」 | ❌ 未找到 | 纯子串匹配，不处理分词 |

**根因有两层**：

1. **检索算法**：`search-docs` 是整串 `str_contains`，需求里几乎不会刚好写成 API 名
2. **词表**（更本质）：能力描述是开发视角，缺业务同义词

**修法**：

- 检索改为**分词匹配**：中文 2-gram + 整块，按命中度排序；带停用词表
  （否则「zzz不存在的东西」会命中「字典不存在」—— 词面命中、意图相反）
- 能力面新增 `also_known_as` **业务同义词**字段：
  - dict → 「运营改文案 / 改显示名 / 状态文案不用发版」
  - operation_log → 「处理留痕 / 谁改的 / 事后能查到谁在什么时候改了什么」
  - upload → 「现场照片 / 传多张图 / 报价单扫描件」

**修复后全部命中**：

```
运营希望自己改文案   HIT 4 条
处理留痕             HIT 3 条
现场照片要能传多张   HIT 2 条
事后能查到谁改的     HIT 2 条
```

> **教训：能力描述要能被「用业务语言提问的人」检索到。**
> 写「把枚举变成一等公民」的是框架作者，写需求的是业务方 ——
> 中间那道鸿沟不能指望 AI 自己跨过去。
>
> 这条与第四轮的「数据源分叉」、第五轮的「校验器沉默」是同一族问题：
> **AI 找不到能力时不会报错，它会自己造一个。**

#### 缺陷 2：能力面谎报「权限节点自动生成」

AI 在 Resource 注释里写了「权限节点自动生成」，但**数据库里实际是 0 个**。

根因：能力面原文是「权限节点由 Resource 注册时**自动生成**，无需手写」——
而实际上必须显式执行 `php artisan aimanong:permission sync`。

措辞已改：

```
naming        → 权限节点名由 Resource 自动推导为 {uri}.{action}，无需手写
requires_sync → 新增/改动 Resource 后**必须执行** permission sync 才会写入数据库；
                不执行则权限列表里看不到该资源
```

> **教训：「自动推导」与「自动写库」是两件事。**
> 含糊的措辞会让 AI 得到一个「看起来对、实际没生效」的结论 ——
> 而它没有任何理由怀疑文档。

## 🔴 本轮最重要的发现：一个严重框架 bug

**5 个互不相识的 agent 全部独立撞到同一个 bug，而我们的测试体系一个都没发现。**

### 现象

Laravel 侧页面里的资源/链接 URL **没有前导斜杠**：

```html
href="admin/assets/css/design-system.css"    ← 相对路径
```

浏览器按当前页面的 baseURI 解析：

| 页面 | 解析结果 | 实际 |
|---|---|---|
| `/admin`（控制台） | `/admin/assets/...` | ✅ 200（base 是 `/`，**碰巧对**） |
| `/admin/articles`（资源页） | `/admin/admin/assets/...` | ❌ **404** |

→ **所有深度 ≥2 的页面完全不可用**：无样式、Vue 加载不到、菜单点不动、登录表单提交到 404。

### 根因

| 驱动 | `urlPrefix()` | 结果 |
|---|---|---|
| ThinkPHP | `'/'.trim($prefix,'/')` | `/admin` ✅ |
| **Laravel** | `$this->context()->prefix()` **未归一化** | `admin` ❌ |

`Aimanong::url()` 直接拼它 → `admin/assets/x.css`。

### 为什么躲过了全部测试

**e2e 只测了控制台页（深度 1）**，而控制台恰好正常 ——
223 个单测 + 147 条 e2e 断言 + 之前的「全面验收」全绿。

**修法**：`LaravelRuntime::urlPrefix()` 归一化（对齐 ThinkPHP 的行为）。
已验证：修后资源页 URL 变成 `/admin/assets/...`，浏览器里 Vue 正常挂载。

> 这条印证了那句老教训：**「全绿」不等于用户能用**。
> 而这次发现它的不是测试，是**5 个真的在浏览器里用产品的人（agent）**。

# 第八轮：修 L3 暴露的问题（树形 + 越权）

**日期**：2026-10-15
**起因**：第七轮把 L3 跑完后，结论是「框架原生只支持 1/5」。按记录里的优先级
清单动手修，**目的不是把分数做上去，而是看修完能不能真的支撑声明式开发**。

## 修了什么

### ① 树形：从「半成品」到真能用

**缺口的确切位置**（这是最值得记的一点 —— 三处都写好了，只差最后一根线）：

| 环节 | 状态 |
|---|---|
| 后端 `tree()` 声明、`/tree` 接口返回嵌套 `children` | ✅ 一直是好的 |
| 前端 `flattenTree()` 算 `_depth` | ✅ 一直在算 |
| design-system 里 `.am-tree-toggle`（连 `aria-expanded=false` 的旋转动画） | ✅ 一直在 |
| **模板使用它们** | ❌ **从没用过** |

证据：`resource.blade.php` 里 `treeTitleColumn` 定义了、也暴露给模板了，
**但模板里一次都没引用**；`_depth` 在整个前端只出现 1 次（赋值处）。

后果：声明了 `tree()` 的页面返回 200、接口正常，**只是看不出层级**。

修法：按 `_depth` 缩进 + 父节点展开/折叠（`displayRows` 过滤被折叠的子孙）。
两端渲染结果逐项一致：

```
缩进=0px   开关=1  总部
缩进=16px  开关=1  研发部
缩进=32px  开关=0  前端组
缩进=16px  开关=0  市场部
```

浏览器实测：折叠「总部」→ 只剩 1 行；再展开 → 回到 4 行；无 JS 报错。

### ② 🔴 tree/move 越权（本轮最严重的发现）

**这是修树形时顺带撞出来的**，不是计划内的。

`tree()` 与 `move()` 漏了 `authorize_()`（控制器其余 7 个动作都有）。
用零权限账号实测：

| 请求 | 修复前 | 修复后 |
|---|---|---|
| `GET /api/departments` | 403 ✅ | 403 ✅ |
| `GET /api/departments/tree` | **200（返回整张表）** | 403 ✅ |
| `PUT /api/departments/4/move` | **200（parent_id 真被改）** | 403 ✅ |

`move` 是**写**操作，所以这条比 tree 更严重 —— 零权限用户可以改数据。

顺带发现 `batch` 也有同类问题：校验声明的动作排在授权之前（未授权用户能靠
403/501 的差别探测出声明了哪些批量动作），且未实现的分支整条路径无授权。

**修法**：补 `authorize_()`；并加**结构性守卫**
`ControllerPermissionCoverageTest` —— 枚举控制器全部公开动作，任何一个没调
`authorize_()` 就红。白名单每项必须写明理由。

> 反例验证：注释掉 `index` 的 `authorize_()` → 测试报 `index` ❌ ✅
> （第一次造反例时我的注入字符串没匹配上、**静默没生效**，差点把假绿当验证通过 ——
> 重做了才确认守卫真的会拦。）

### ③ 顺带：一个会删空产物的脚本 bug

`blade2think.py` 用 `sys.argv[1]` 当输入目录且**没有参数校验**。传一个不认识的
参数（如 `--check`）时 glob 找不到文件，但它**先执行了 `rmtree(OUT)`** ——
产物被清空且不重建，只打印「合计 0 个模板」。

我自己就踩了：一条 `--check` 把 10 个 TP 模板全删了（已从 git 恢复）。
已修：**先确认有东西可生成，再动产物目录**。
反例验证：传 `--check` → 拒绝执行且产物数 10 → 10 不变 ✅

只能自己再写一套（那「同一份声明两端行为一致」就是空话）。已移入 core。

# 第九轮：把 L3 缺的两项能力补成声明式

**日期**：2026-10-15
**目标**：第七轮结论是「框架原生只支持 1/5」，第八轮修了树形。
这轮补 **L3-2（条件显示）** 与 **L3-5（按钮级权限）** —— 这两项原本
每个项目都得自己写扩展/中间件。

## 做了什么

### ① 条件显示：从「自己写扩展」到一行声明

```php
$form->select('priority')->visibleWhen('type', 'bug');
$form->select('priority')->visibleWhen('type', ['bug', 'feature']);   // 其中之一
```

被条件藏起来的字段**提交时清空** —— 否则会把用户在界面上根本没看到的值写进库
（把 type 从 bug 改回 feature，priority 仍带着上次的 high）。

浏览器实测：初始 `[标题,类型,描述]` → 切 bug `[…优先级…]` → 切 feature 消失 → 再切回来出现。

自省接口的 `form_options` 也补上了这一项（L3-2 那个 agent 翻过这份清单，
当时里面什么都没有）。

### ② 按钮级权限：无需声明

权限节点 `{uri}.{action}` 框架本来就会生成 —— 页面直接按它决定渲染哪些按钮。
**服务端不渲染**（不是 CSS/JS 藏起来：那样 DOM 里还在、Vue 重渲染还会回来）。

实测（两端一致）：

```
受限账号（只有 departments.index）：openCreate / edit / remove / 操作列头 全部不输出
超管：三个都在
```

### 🔴 ③ 顺带挖出：ThinkPHP 的 RBAC 从来没生效过

这是在验①②的过程中撞出来的 —— 要给一个非超管账号**开**权限，
才发现「怎么开都没用」。往下挖出**三个叠在一起的 bug**：

| # | Bug | 表现 |
|---|---|---|
| 1 | TP 的 `belongsToMany` 后两个参数语义与 Laravel **相反** | 四个关联全写反 → 生成的 SQL 把键对调 → 「角色有哪些权限」**恒为空**，不报错 |
| 2 | 没有权限节点同步入口 | TP 压根没有 `aimanong:permission` 命令 → 节点永远建不出来 |
| 3 | demo 脚本插 pivot 漏 `user_type` | 角色看起来绑上了，实际读不出来 |

其中 1 最阴：它**可能碰巧查对**。`$user->roles` 就返回了正确角色
（role id 与 user id 恰好都是 2），让人以为关联没问题 —— 直到去查
`$role->permissions` 才发现恒为空。

**而这在测试里看不出来**：e2e 断言的是「普通角色被拒」，
而「权限生效」与「谁都没权限」产生的结果**完全一样**。

> 教训：**「断言了拒绝」不等于「验证了权限系统」。**
> 只有同时验证「有权者能进」和「无权者被拒」，才证明得了。
> 这条已写进 CHANGELOG。

修完之后的链路：
`viewer` → 角色 `viewer` → 权限 `admin.departments.index` ✅

## 结论

### 1. 严格口径下「一次成功率」仍然是 0/5

5 题都需要多轮迭代才通过首次校验。**这不是模型的问题，也不是框架的问题** ——
L3 的题面本身就是复合需求（建表/建模/写声明/注册/验证/排除干扰），
单轮完成反而不现实。

**所以「一次成功率」这个北极星指标值得重新定义** ——
它把「迭代中自愈」也算成失败，而这个框架的核心卖点恰恰是**自愈**。
更合适的指标可能是：

- **无需人工介入的交付率**（本轮 5/5）
- **是否退化为读源码**（本轮 0/5 退化，第七轮 1/5）
- **是否需要写框架不认识的代码**（本轮 1/5，第七轮 4/5）

### 2. 真正的答案是：**框架能力 ≈ AI 表现的决定项**

同一个模型、同样的题、同样的约束，只把框架的三个缺口补上，
三题的调用数降了 30~55%、报错数降了 42~70%；
而没补的两题纹丝不动。

这比任何「六轮实测 1.0」都更能说明这个项目的价值在哪：
**它的上限不取决于 AI 多强，而取决于声明层覆盖了多少。**
