# CRM 真实场景验证（第三件）

> 2026-10-11 · 框架版本 v1.6.0
>
> 目的：用一套**完整 CRM 业务**压力测试 v1.6.0 新增的六项基座能力，
> 找出「示例场景永远发现不了」的短板。

---

## 一、方法论

沿用第一件（电商场景）的做法：

1. 先用**业务语言**写需求，再动手实现 —— 不迁就框架调整需求
2. 刻意设置**框架可能做不到**的需求，用来定位能力边界
3. 每个需求都**真机跑一遍**，不以「能编译」为准
4. 发现的缺陷当场修，并补回归测试

与第一件的区别：这次的主要变量是 **v1.6.0 的六项基座能力**
（字典 / 上传 / 审计日志 / 个人中心 / 用户管理 / 只读资源），
以及**多表关联的深度**。

---

## 二、场景设计

五张表，覆盖真实 CRM 的复杂度：

| 表 | 关键点 |
|---|---|
| `crm_customers` 客户 | 软删除、字典字段（等级/行业/状态/来源）、单图、region 三级地址、金额 |
| `crm_contacts` 联系人 | 外键、布尔标记（主要联系人）、头像 |
| `crm_opportunities` 商机 | 外键、**多对多**（对接人）、金额阈值高亮、进度条 |
| `crm_followups` 跟进记录 | 外键（可选）、**多文件**附件、时间戳 |
| `crm_contracts` 合同 | 唯一编号、**日期区间**、单文件、导出 |

配套 7 个代码声明字典：`crm_level` / `crm_industry` / `crm_customer_status` /
`crm_source` / `crm_stage` / `crm_followup_type` / `crm_contract_status`。

## 五、发现并修复的缺陷（4 个）

每一个都是「界面看着正常、测试全绿」的类型。

### 缺陷 1：条件高亮从来没有过视觉效果（三层问题叠加）

`dangerWhen()` / `dangerBelow()` / `warningAbove()` 是**第一件真实场景验证
专门加出来**的能力（需求：「库存少于 10 要标红」）。这次用它做
「商机金额超 100 万标红」，发现它**一次都没生效过**。

三层原因，缺一层都修不好：

| 层 | 问题 | 修复 |
|---|---|---|
| JS | 产出 `hl-danger` | CSS 里叫 `.am-hl-danger`（BEM 命名空间）→ 改成 `am-hl-danger` |
| CSS | 特异度不够 | `.am-hl-danger`(0,1,0) 被 `.am-table td`(0,1,1) 覆盖颜色——**字重生效了、颜色没有**，看起来像「高亮只是加粗」→ 改为 `.am-table td.am-hl-danger` |
| 缓存 | 改了看不到 | 资源路由是 `Cache-Control: public`，用户升级后**仍加载旧 CSS** → 资源 URL 加 `?v=<版本号>` 缓存击穿 |

> 第二层尤其阴险：字重变了，所以肉眼看「确实有点不一样」，
> 很容易误判成「功能正常，只是颜色不够明显」。

### 缺陷 2：`daterange` 没有列契约

```php
$form->dateRange('period');   // 前端硬编码绑定 period_start / period_end
```

真实表里是 `start_at` / `end_at` —— 表单能渲染、提交永远存不进去，
`ai:verify` 还报一个莫名其妙的 `SUSPECT_FIELD('period')`。

修复：`->columns('start_at', 'end_at')` 显式声明，
验证器按声明的列检查（而不是检查字段名本身）。

### 缺陷 3：数值字段留空 → NOT NULL 违约

CRM 商机的「赢单率」滑块没动过，提交时报：

```
NOT NULL constraint failed: crm_opportunities.probability
```

链路：数值字段初始化为空串 → Laravel 的 `ConvertEmptyStringsToNull` 变成 `null`
→ 撞 NOT NULL。

修复：
- 数值类字段（`number` / `decimal` / `money` / `rate` / `slider`）无默认值时初始化为 `0`
- NOT NULL 违约给出**中文字段名 + 两种改法**，不再把 SQL 抛给用户

### 缺陷 4：`->dict()` 让 CSV 导出退回英文

`dict()` 最初写的是 `map()` 再 `badge()`，而 `badge()` 会把 formatter
覆盖成 `'badge'` —— 导出器只在 formatter 为 `map`/`enum` 时才套用中文映射。

界面上是「商务谈判」，导出文件里是 `negotiation`。
前端三种 formatter 都走 `mapLabel`，所以**只有导出会坏**。

修复：
- `dict()` 改为「先 badge 再 map」
- 导出器对 `badge` 也检查 `props.map`（两种书写顺序都正确）

### 附带：多文件上传被客户端预检误拦

`->files('attachments')->accept('pdf,jpg,png,docx')` 的字段，
上传 png 时**客户端直接拒绝**（预检只看全局白名单，而全局白名单里没有 png），
服务端一次请求都收不到，用户只看到「数量没变」。

界面上有一行红色小字，但在表单底部、很容易被忽略。

修复：预检优先使用字段自己的 `accept`。
同时把 `images` / `files` 也纳入「多值字段初始化成数组」的分支。

## 七、结论

### 1. v1.6.0 的六项基座能力在真实场景下站得住

字典、上传、审计、只读资源都被真实需求用到了，
而且**字典与上传是这次 CRM 的主力** —— 没有它们，
光「客户等级要分色」「跟进记录要传照片」这两条就得写不少代码。

### 2. 但「声明能编译」与「功能可用」之间仍有距离

这次 4 个缺陷里，**3 个的界面表现都是「看起来没问题」**：

- 高亮：类名对了、字重变了，只有颜色没变
- 字典导出：界面中文正确，只有导出文件是英文
- 多文件上传：界面有红色小字，容易被忽略

> **只测「能不能打开页面」，永远发现不了这些。**
> 必须端到端跑一遍并核对**落库结果**。

### 3. 「加了一个能力」不等于「这个能力能用」

`dangerWhen()` 是第一件验证加的能力，到第三件才被发现从未生效。
原因是当时的验收方式是「类名加上了」而不是「颜色变了」。

> 验收标准要盯着**用户可感知的结果**，不是中间产物。

### 4. 覆盖率未达 90% 是事实

差的三项（报表 / 定时提醒 / 分组视图）都是 P1 范围。
记在这里，不当作已支持。
