# UI 美化 + 基座功能 方案

> 针对用户反馈的两点：
> 1. 「整个页面很丑」→ 要求现代感/科技感/炫酷感，最好可选风格
> 2. 「参考竞品补齐基座功能」

---

# 第一部分：UI 美化方案

## 1.1 诊断：为什么"丑"（全是量化数据）

| 症状 | 数据 | 后果 |
|---|---|---|
| **零设计 token** | CSS 变量 **0 个** | 改一个颜色要翻 25 处 |
| **色值散乱** | **25 个**不同色值，`#dde3e0` 出现 15 次 | 没有色板，视觉不统一 |
| **CSS 三份重复** | 登录/首页/列表页各写一套，零复用 | 改一处要改三处 |
| **间距无网格** | 8/9/12/14/16/24/40px 混用 | 节奏混乱，显得随意 |
| **圆角无规范** | 3/4/6/8/10/12px **六种** | 应该是 2-3 档 |
| **阴影仅 2 种** | 且随手写 | 没有层次感（卡片/弹窗应不同） |
| **动效几乎为零** | `transition` 2 处、`animation` **0 处** | 页面"死板"，这是廉价感主因 |
| **无暗色模式** | `dark` 关键词 **0** | 2025 年后台没有暗色不可接受 |
| **emoji 当图标** | 📝🗂👤🏷 | 跨平台渲染不一致、无法控色、显廉价 |
| **中文字体栈不全** | 缺 Noto Sans SC / 思源 | Linux 环境退化 |
| **行高未适配中文** | 1.5（英文标准） | 中文应 1.6-1.75 |

**根因归纳**：没有 token 层 → 没有层次体系 → 没有动效 → 没有暗色 → 用 emoji 凑图标。

## 1.2 已完成的视觉原型（三套风格，可实际切换）

我已经做出**可运行的原型**，三套风格通过 `data-theme` 切换，**DOM 完全不变**：

| 风格 | 气质 | 主色 | 关键特征 | 适合 |
|---|---|---|---|---|
| **青瓷** `celadon` | 克制·专业 | 深青 `#0d9488` | 大量留白、细腻阴影、无干扰 | 传统企业、政务、后台长期使用 |
| **深空** `deepspace` | 科技·炫酷 | 青绿 `#2dd4bf` | 暗色底 + 网格纹理 + 光晕边框 | 开发者工具、监控、演示 |
| **极光** `aurora` | 现代·活力 | 紫 `#7c3aed` | 顶部流动渐变光带 + 玻璃拟态 | SaaS、面向 C 端品牌的后台 |

## 1.3 技术实现建议

| 选项 | 优点 | 缺点 | 评估 |
|---|---|---|---|
| a) 全手写 CSS + 变量 | 完全可控、零依赖 | 工作量大 | 可行 |
| b) Tailwind CDN | 开发快 | **体积大（300KB+）、CDN 依赖、离线不可用** | ❌ 不适合框架 |
| c) Pico/Water.css | 现成 | 风格固定、难定制、不适合后台 | ❌ |
| **d) 内联自研设计系统** | 零依赖、体积小（~15KB）、完全可控 | 需自己写 | ✅ **推荐** |

**推荐 d**，理由：
1. 后台框架的 UI 需求是**收敛的**（表格/表单/弹窗/卡片/标签），不需要通用 CSS 框架
2. 保持"零构建步骤"（Vue 是 CDN 内联的，加 Tailwind 就得加构建）
3. 15KB 内联 CSS 对首屏影响可忽略，且能用浏览器缓存

**落地形式**：
```
resources/views/partials/design-system.blade.php   ← 设计系统（token + 组件）
resources/views/partials/layout.blade.php          ← 布局（header + sidebar）
resources/views/partials/icons.blade.php           ← 内联 SVG 图标集
```
用 `@include` 复用，消灭三份重复。

**主题切换**：
- 服务端：`config('aimanong.ui.theme')` 或用户偏好存 DB
- 客户端：右上角切换器，写入 `localStorage` + `data-theme`
- 暗色模式跟随系统：`prefers-color-scheme`

## 2.3 判断标准（关键）

不能只看"竞品有"，还要过**两条我们的特有标准**：

1. **能否声明式表达？**（不要黑盒配置）
2. **AI 能否自省？**（AI 怎么知道它存在、怎么用对）

一个功能如果只能靠人读文档学会，就**不适合这个框架**。

## 2.4 推荐清单

### 🟢 P0 必做（事实标准 + 契合 AI 定位）

| 功能 | 竞品覆盖 | 为什么必做 | 声明式设计 |
|---|---|---|---|
| **个人中心** | 100% | 连改密码都没有，说不过去 | 内置 Resource |
| **操作日志** | 100% | 审计刚需；**AI 可用它调试"为什么数据变了"** | 自动记录（声明式开关） |
| **登录日志** | 100% | 安全刚需，与操作日志同源 | 自动记录 |
| **数据字典** | 90% | **最契合 AI**：把枚举变成一等公民，AI 能自省有哪些可选值；消除各 Resource 硬编码 options | `->dict('order_status')` |
| **文件上传** | 95% | 现在 image 字段**没有上传能力** | `->upload('images')` |
| **用户管理增强** | 100% | 现只有 5 字段，缺邮箱/手机/最后登录 | 扩展表 + 内置 Resource |

### 🟡 P1 推荐（有价值但可延后）

| 功能 | 说明 |
|---|---|
| **系统配置** | 键值对参数，声明式 `config('aimanong.setting.xxx')` |
| **通知公告** | 后台内通知，与操作日志共用"消息"抽象 |
| **部门/组织架构** | 树形 + 数据权限基础，但**很多项目用不上** |
| **定时任务可视化** | 管理 Laravel Schedule，但要小心权限 |
| **数据权限（行级）** | 已有 `ScopeHooks` 钩子，可做成开箱即用的"本部门/本人"预设 |

### 🔴 不做 / 谨慎

| 功能 | 为什么不做 |
|---|---|
| **工作流/审批流** | 做浅了没用，做深了是无底洞（Flowable 那种是另一个产品） |
| **多语言** | 核心用户是中文生态，投入产出比低 |
| **岗位管理** | 部门已够用，岗位是若依的历史包袱 |
| **在线用户** | 与 session 驱动强耦合，收益低 |
| **IM/支付/商城** | 那是业务，不是基座（yudao 有是因为它是低代码平台） |

## 2.5 分阶段实施

### 阶段 1：UI 设计系统（**先做这个**）
- 建 token 层 + 组件 + 图标集
- 三套主题 + 暗色
- 改造全部页面
- **为什么先做**：视觉是用户第一印象，且后续所有新功能都复用它

### 阶段 2：P0 基座（6 项）
- 个人中心、操作日志、登录日志、数据字典、文件上传、用户增强
- 都用 Aimanong 自己的 Resource 实现（吃狗粮）
- **工作量大头**：文件上传（存储抽象）+ 数据字典（缓存 + 声明式接入）

### 阶段 3：P1 补齐（按需）
- 系统配置、通知公告、部门+数据权限
- 视用户反馈决定优先级

# 第三部分：我的建议

## 先做 UI，再做基座

理由：
1. **UI 是当前最痛的点**（用户第一句就说"很丑"）
2. UI 是**所有后续功能的地基**——基座功能也要用这套设计系统
3. UI 改造**不改变任何后端契约**，风险低

## UI 阶段的具体建议

1. **风格默认用「青瓷」**（克制专业，最不容易看腻）
2. **「深空」作为可选**（开发者/演示场景很出彩）
3. **「极光」作为可选**（SaaS 品牌感）
4. **暗色模式独立于风格**（任何风格都能切暗色）

## 需要你决策的点

1. 三套风格是否都要？还是先做 1-2 套？
2. 默认风格选哪个？
3. UI 和基座**串行**（先 UI 后基座）还是**并行**？
4. P0 的 6 项基座功能，有没有你想砍掉或提前的？

# 第四部分：竞品调研补充（调研报告核实后）

调研报告：[竞品基座调研与取舍.md](竞品基座调研与取舍.md)（925 行 / 33 张表格）

## 4.1 我核实过的硬证据

| 证据 | 我的核实结果 |
|---|---|
| 若依按"血统"加权后覆盖度要下调 | ✅ 成立——yudao README 自述基于 RuoYi-Vue，不是独立选票 |
| PHP 阵营 vs Java 阵营是两种生态 | ✅ 成立——字典/岗位/部门是 Java 惯例，PHP 阵营（dcat/Filament/Nova/Django）零覆盖 |
| dcat-admin 没有数据字典 | ✅ 成立（全仓库 grep 零命中） |
| Filament 3 无 RBAC 表、无 2FA | ✅ 成立（源码树实测） |
| 数据权限在竞品中 100% 是付费项 | ✅ 成立（Pig README、Lamp 对比页原文） |

## 4.2 三条反直觉结论 —— 我认为都对，但有一条根因更深

### 结论一：数据字典覆盖率仅 3/8，但必须做 ✅ 同意，且根因比报告更深

报告的理由是「把散落的 `->options()` 收束成 AI 可自省的一等公民」。

**我实测发现的问题更严重**：同一个字段在 `grid()` 和 `form()` 里**各声明一遍**：

```php
// CmsArticleResource.php
$grid->column('status', '状态')->badge()->map(ArticleStatus::options());   // 第 64 行
$form->select('status')->label('状态')->options(ArticleStatus::options()); // 第 84 行
```

**连中文标签 `'状态'` 都写了两遍。**

→ 所以数据字典不是"引入新风险"，而是**解决已有的分叉风险**。
→ 但报告的警告仍然成立：如果不做「字段级单一来源」，字典只是把 2 处重复变成 3 处。

**我的加强方案**：数据字典必须与「字段声明去重」一起做，
否则等于在一个已经有分叉的地方再加一个数据源。

### 结论二：可视化表单设计器不做 ✅ 完全同意

关键区分非常精准：
- 产出**代码**的生成器 ✅（dcat `admin:scaffold`、我们 `scaffold_resource`）
- 产出**数据库 JSON** 的设计器 ❌（若依表单构建、Jeecg Online 表单）

后者会让"表单长什么样"变成数据库里的一坨 JSON —— **AI 读不到、git diff 看不到、无法 review**，
与我们「声明式 + 可自省」的根基冲突。

### 结论三：数据权限不做预置策略 ✅ 同意，理由比报告更强

报告理由是「`cannotVerify` 已承认无法验证，加了会制造假绿灯」。

**我补充一条**：v1.2.0 已经提供了 `ScopeHooks`（数据作用域的官方注册点）。
再加一套"预置策略"就是**两套隔离机制**，用户不知道该用哪个 —— 又是一次分叉。

→ 正确做法：**保持 `ScopeHooks` 是唯一入口**，只补文档和示例，不加预置策略。

## 4.3 报告提出的最高风险 —— 我的处置

> 「数据字典会引入第二个枚举数据源（PHP Enum + dict 表），违反单一数据源」

报告给了三条解药，我全部采纳并**加一条**：

1. ✅ **按"谁来改"划界**：开发期固定的枚举用 PHP Enum；运营期需要改的用 dict
2. ✅ **`ai:verify` 检测双声明** → 报 `DUAL_ENUM_SOURCE` 编译期错误
3. ✅ **`/__ai/dict` 暴露全部值**（AI 可自省）
4. ➕ **新增：字段声明去重**（我的补充）——
   同一字段的 label/map/options 应能声明一次、grid 与 form 共用，
   否则字典只是让分叉从 2 处变 3 处

## 4.4 一个新发现的设计约束（建议写进 AGENTS.md）

报告发现菜单有两种流派：

| 流派 | 代表 | 缺点 |
|---|---|---|
| **DB 驱动** | 若依 / Jeecg / yudao / Pig / Lamp / dcat | 菜单是数据，git diff 看不到，AI 读不到 |
| **代码声明** | Filament `navigation()` / Nova / Django | 好，但配置分散 |
| **我们 `Resource::menu()`** | Aimanong | **第三条路：既能被 AI 读到、能 git diff，又零额外配置** |

→ **建议明确约束：将来若有人提议"加可视化菜单管理页"，答案是「不」。**
那会让菜单变成"代码一份 + 数据库一份"，正是 `SingleSourceOfTruthTest` 防的事故。

## 4.5 实施节奏的修正

报告指出：**阶段 A 的 6 项必须一起做**，因为它们互相咬合：

```
用户增强 ← 需要文件上传（头像）
文件上传 ← 需要操作日志（谁传了什么）
个人中心 ← 读操作日志（我的操作记录）
数据字典 ← 与上面 4 项共用一次三处接线
```

分开做 = 15 个接线点做 5 遍 = **5 次数据分叉的机会**。

**我同意这个判断**，并调整方案为：

| 阶段 | 内容 | 说明 |
|---|---|---|
| **阶段 1** | UI 设计系统（三套主题） | 不变，仍先做 |
| **阶段 2** | **A 组 6 项一起做** + 字段声明去重 | 按报告建议合并，加我的补充 |
| **阶段 3** | B 组推荐项（按需） | 系统配置/通知公告等 |
