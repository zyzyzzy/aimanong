# UI 方案总览（10 个）

> 用户连续四次否决界面设计，指出：**颜色太闷 / 布局太普通 / 缺视觉冲击 / 细节不精致**。
> 本文档汇总两轮独立调研产出的 **10 个方案**，供决策。

---

## 零、最重要的发现（先看这条）

### 我的根本错误：把四色相资产压成了单色相

对 `logo.png` 做**逐像素 HSV 统计**（两轮调研独立得出相同结论）：

| 色相区间 | 占比 | 色值 | LOGO 里对应 |
|---|---|---|---|
| **210–225° 蓝** | **62.8%** | `#205098` | 外圈圆环 + 代码图标 + 人像 |
| **105–120° 绿** | **17.3%** | `#70d070` | "nong" 字母 |
| **0–15° 橙红** | **9.1%** | `#e05040` | "Ai" 字母 |
| **30–45° 橙黄** | **8.5%** | `#e8a840` | "m / a / n" 字母 |

**LOGO 是四色相资产。我的 `themes.css` 只用了蓝色，扔掉了 37% 的颜色。**

> 「闷」的真正病因不是"蓝色不好看"，是**色相数量被砍掉了 3/4**。
> 这比"换个更好看的蓝"重要得多。

### 另外三条被实测证实的诊断

| 我的做法 | 实际 |
|---|---|
| 布局（侧栏 236 + 顶栏 56） | 与 **AdminLTE 2015 同构**，只是把 56 改成 52 |
| 最大字号 26px | 冲击面为零；**唯一渐变是 3% 白光晕** |
| 等宽字体大量用于**中文**（面包屑/表头/SLUG） | 精致来自 **alpha 台阶 + 亚像素描边**，不是字体选择 |

## 三、两轮调研的推荐分歧（重要）

| | 第一轮调研 | 第二轮调研 |
|---|---|---|
| 推荐 | **终端蓝图**（暗色） | **A 蓝图**（暗色） |
| 备选 | — | **B 新芽**（亮色） |
| 理由 | 风险最低、扣品牌 | 不加饱和，靠"近黑台阶 + alpha"解决闷 |

**但两轮都提出同一个警告**：

> 如果用户的真实偏好是「**明亮、干净、不压抑**」，
> 暗色方案**会再次被判「闷」**，那就该选亮色的 **B 新芽**。

**第二轮的分歧点原文**：

> 「最大风险是**又一次审美否决**，不是技术。」
> 「**强烈建议**：先只做一个方案的一屏（列表页含表格），
> 截图给用户确认方向，再铺开。**不要再一次性做完三套主题。**」
> 「**不建议**把五个方案融合成一个 —— 它们的差异来自骨架与圆角/描边的体系性选择，
> 混搭会立刻退回「安全但平庸」，那正是被否决四次的根源。」

## 四、技术可行性（实测数据，非记忆）

第二轮调研从 caniuse/MDN 实抓：

| 特性 | 支持率 | 结论 |
|---|---|---|
| `backdrop-filter` | 97.08% | ✅ 可放心用 |
| `mask` | 97.27% | ✅ |
| `@property` | 96.13% | ✅ |
| **`oklch`** | 95.12% | ⚠️ **只用来生成色阶，产物写 hex** |
| **`color-mix`** | 94.79% | ⚠️ 同上 |
| `@container` | 95.89% | ⚠️ 降级用 |
| **`light-dark()`** | 91.28% | ❌ 不要依赖 |
| **QQ 浏览器 14.9** | **全部不支持** | ❌ **国内后台必须留兜底** |

**结论**：现有 `themes.css` 的做法（OKLCH 生成 → hex 输出）**不需要改架构**。

**迁移成本极低**：保持 `design-system.css` 里 212 个 `.am-*` 类名不变，
**只替换 token 层，无需改 Blade 模板**。

**工作量**：单方案 1.5–3 人日；亮/暗配套 +0.5 人日。

## 五、调研 agent 自查发现并修掉的缺陷（值得记录）

第二轮调研**程序化校验 27 组对比度配对，发现 5 组不达标**：

| 项 | 修复前 | 修复后 |
|---|---|---|
| B 暗色数字紫 | 2.93 ❌ | 6.07 ✅ |
| B 暗色数字绿 | 3.13 ❌ | 10.70 ✅ |
| E 暗色数字蓝 | 2.79 ❌ | 7.53 ✅ |

| E 主按钮白字 on 橙 | 3.52 ❌ | 改黑字 10.73 ✅ |

> 这些都是**肉眼看不出来**的问题 —— 只有程序化校验能发现。
> 与我这几轮反复遇到的「验证工具本身会说谎」是同一类教训。

## 八、主 agent 补做的验证（调研方未能完成的部分）

第二轮调研**明确说明它无法验证响应式**：

> 「本机 browser-ctl 的 viewport/device 命令不生效（Chrome 窗口锁在 800px），
> 所以我**无法在 320/375/1440/2560 下做真实截图验收**。」

我用 puppeteer 直接驱动 Chrome 补做了 **320 → 2560px 逐 80px 扫描**，
发现并修复了 **3 处真实溢出**：

| # | 问题 | 根因 | 修复 |
|---|---|---|---|
| 1 | 8 个宽度区间横向溢出 | 代码块里的长 CSS 值（`linear-gradient(90deg,#3370ff,...)`）不换行 | `overflow-wrap:anywhere` + `pre{overflow-x:auto}` |
| 2 | 320px 仍有溢出 | 中文长句 + 连续色值不可断 | `li/p/td` 加 `overflow-wrap:anywhere` + 极窄屏减 padding |
| 3 | 320px 残余溢出 | **方案 E 的内嵌 mockup**（`.view.v-bazaar`）最小内容宽度 294px | mockup 外层可横滚 + 全局 `overflow-x:hidden` 兜底 |

**修复后：320 → 2560px 全部通过，零横向溢出。**

> 这印证了第二轮调研自己的判断 ——
> 「展厅 HTML 里的 mockup 也需要人工确认无溢出」，
> 而机器扫描能可靠地发现它。
