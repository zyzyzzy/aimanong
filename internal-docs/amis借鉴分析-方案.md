# amis（百度低代码框架）借鉴分析

> 2026-10-16 · 基于对 `baidu/amis` 仓库、官方文档（8 份核心文档 / 约 4700 行）、npm 包实测、
> 以及社区「amis + AI」实践文章的核对。所有数字为实测。

---

## 〇、结论先行

| 问题 | 结论 |
|---|---|
| amis 和我们是同类吗？ | **同源，但分叉成了两种解法** —— 都是「配置驱动前端」，但它选「大词表 + 外部 AI 兜底」，我们选「小词表 + 内建校验」 |
| 我们该改用 amis 吗？ | **不该。** 它的 73.74MB / 38 依赖 / 5.5MB SDK 与「零构建」直接冲突 |
| 我们该照它的规模扩词表吗？ | **不该。** 它 120 个组件正是它 AI 学习成本高的**原因**（有实测证据） |
| 有值得抄的吗？ | **有，6 件。** 最大一件是**页面级结构词汇** —— 这是我们的真实缺口 |
| 最该先做哪一件？ | **页面级词汇（`layout`/`tabs`/`cards`）+ 补上 `Show`（详情页）的渲染方** |

**一句话**：amis 用 **120 个组件**换表达力，代价是 AI 学不会、JSON 错一个字段就白屏；
我们用 **30 个字段类型**换可验证性，代价是**页面结构表达不出来**。
所以：**抄它的结构词汇，别抄它的规模和实现。**

## 一、amis 是什么（实测画像）

| 项 | 实测值 |
|---|---|
| 仓库 | `baidu/amis` · **18890 stars** · 2732 forks · Apache-2.0 |
| 语言 / 规模 | TypeScript · 仓库 **192 MB** |
| 生命期 | 2019-04 建仓，**至今仍在维护**（最近推送 2026-03） |
| 定位（README 原文） | 「前端低代码框架，通过 JSON 配置就能生成各种后台页面……**甚至可以不需要了解前端**」 |
| npm 现状 | `amis@6.13.0` · 解包 **73.74 MB** · **839 个文件** · **38 个依赖** |

**包结构**（`packages/`）：

```
amis-core           引擎（渲染器注册、数据域、表达式求值）
amis                组件库（85 份组件文档，文章称内置 120 种组件）
amis-formula        表达式 / 公式引擎（独立包 —— 说明这块很重）
amis-ui             基础 UI 组件
amis-editor         可视化编辑器
amis-editor-core    编辑器内核
amis-theme-editor-helper   主题编辑器
office-viewer / vite-plugin-amisr / ...
```

**核心模型**（`concepts/schema.md`）：一切皆 `{type: "xxx", ...props}` 递归树。

```json
{ "type": "page", "body": { "type": "tpl", "tpl": "Hello World!" } }
```

**SDK 实测体积**（外链模式，不依赖 npm）：

| 文件 | 原始 |
|---|---|
| `sdk.js` | **2011.5 KB**（gzip 0.54 MB） |
| `sdk.css` | **2520.4 KB** |
| `helper.css` | **947.9 KB** |
| **合计** | **≈ 5.5 MB** |

**对照我们**：`packages/core/resources/assets/` 总共 **1.0 MB**
（Vue 164 KB + `design-system.css` gzip 16.1 KB + `themes.css` gzip 2.6 KB）。

## 二、同源分叉：一张对比表

| 维度 | **amis** | **Aimanong** | 谁更好 |
|---|---|---|---|
| 配置语言 | **JSON**（人手写 / 编辑器生成） | **PHP 声明**（AI 写） | ✅ **我们**：PHP 有类型检查、IDE 补全、静态分析；JSON 没有 |
| 词表规模 | 120 组件 / **85 份文档** | **30 个字段类型** + 26 个列方法 | ⚠️ 各有取舍，见下 |
| 词表覆盖 | **页面 / 布局 / 容器 / 字段 / 动作**全覆盖 | **只有字段与列** | ❌ **amis**：我们缺页面结构 |
| 校验 | 无内建（社区只能**外挂** JSON 验证） | **`ai:verify` 内建** + 219KB 自省 | ✅ **我们** |
| 数据来源 | 纯前端，靠 `api` 配置逐个组件取数 | 后端 Resource 统一出 | ✅ **我们**：单一真源，不会前后端分叉 |
| 权限 / RBAC | **没有**（文档里「权限」全是业务数据示例） | 内建 RBAC + 按钮级 + 菜单级 | ✅ **我们** |
| 条件显示 | `${}` 任意表达式 | `visibleWhen(field, value)` **仅等值/包含** | ❌ **amis** |
| 展示模式 | `crud` 一个 `mode` 切 table/list/cards | **无** | ❌ **amis** |
| 详情页 | `show` / `detail` 组件 | `Show` 类**声明了但没有渲染方** | ❌ **amis** |
| 主题 | 主题编辑器 + CSS 变量 | 141 token，但**承诺的 3 套主题没发货** | ⚠️ 打平（我们做了但没发全） |
| 编辑器 | 可视化编辑器（成熟） | 无 | ❌ **amis**（但见「不该抄的」） |
| 体积 / 依赖 | 73.74 MB / 38 依赖 | **1.0 MB / 0 运行时依赖** | ✅ **我们** |
| 构建 | React + npm 构建（但**也**提供 SDK 外链） | **零构建** | ✅ **我们** |
| AI 支持 | **官方没有**；社区自建 MCP server / Claude Skill | **MCP server 内建** + `llms.txt` + `AGENTS.md` | ✅ **我们** |

### 一个关键发现：amis 走的正是我们刚诊断出的坑

我找到一篇 2025-11 的社区实践，
[当AMIS遇见AI智能体](https://juejin.cn/post/7576559408660201524)
（信也科技），他们给 amis 做 AI 生成时踩的坑，**逐条对应我们已有的解法**：

| 他们的原话 | 我们的现状 |
|---|---|
| 「AMIS平台**内置120种组件**，需手动摸索组件拖拽逻辑，**组件的学习成本较高**」 | 30 个字段类型，`capabilities.json` 自省 |
| 「AMIS依赖于严格的JSON配置结构，**任何格式错误或字段不匹配都会导致渲染失败**」 | PHP 声明 → **编译期**就报错，`ai:verify` 事前拦截 |
| 「直接调用大模型效果展示：**各种乱码**」 | PHP 有类型系统 + 静态分析 + `did_you_mean` |
| 他们的解法：**外挂**「UI设计Agent」+「AMIS生成Agent」+ JSON 验证工具类 | 我们**内建**在框架里，不是外挂 |

> 社区还做了 [amis-mcp-server](https://lobehub.com/zh-TW/mcp/xiaoguan521-amis-mcp-server)、
> [Amis Helper Skill](https://www.skillavatars.com/skills/amis-helper)
> —— 都是因为**词表太大，AI 需要额外脚手架**。

**所以：不要改成 amis，也不要照它的规模扩词表。** 那会把我们推向它已经踩过的坑。

## 三、但有 6 件事值得直接抄

按「对我们 AI 复杂度的贡献」排序。

### 抄 1：页面级结构词汇 ← **最大缺口，建议第一个做**

**为什么**：这是我们词表的**结构性空白**。实测命中数：

| 概念 | amis | 我们 |
|---|---|---|
| `tabs`（标签页） | ✅ | **0 命中** |
| `wizard`（向导） | ✅ | **0 命中** |
| `card` / `panel` / `portlet`（卡片容器） | ✅ | **0 命中** |
| `chart`（图表） | ✅ | **0 命中** |
| `grid` / `hbox` / `flex`（布局） | ✅ | 2 命中（非声明层） |
| **`Show`（详情页）** | ✅ `show`/`detail` | **类存在，但没有任何渲染方** |

**后果**：AI 要做「一个带标签页的详情页」，词表里**没有对应概念** → 只能去写 Blade。
这正是你说的「AI 不得不关心前端实现细节」。

而 `Show` 的情况更值得注意：**它是一个"声明了但没有渲染方"的 API**
—— 和之前发现的 13 个死 prop **完全同类**。
AI 写 `Show::fields(['name','status'])`，进 schema、过校验、**页面上什么都不出现**。

**抄什么**：不是抄 85 个组件，而是抄 **amis 的"容器即 schema"思想** ——
容器组件的 `body` 可以再是一棵 schema 树。

```php
// 在 Resource 上（示意）
public static function layout(): array
{
    return Layout::tabs([
        'basic'   => ['label' => '基本信息', 'fields' => ['name', 'code']],
        'detail'  => ['label' => '明细',     'grid'   => 'order-items'],   // 嵌套另一个 Resource
    ]);
}
```

**关键词**：**最小集**。我建议只做 `layout()` 一个声明 + 三种容器
（`tabs` / `cards` / `sections`），**不做 85 个**。
理由见第六节「词表预算」。

**估工**：3–5 人日（后端声明 + schema 产物 + PHP→Blade 与 TP 双端渲染 + e2e）。
**验证**：e2e 断言渲染产物里出现 `data-tabs` 结构；两端对拍。

---

### 抄 2：`mode` —— 一个字段切三种展示

**为什么**：amis 的 `crud` 用 `mode: table | list | cards`，**同一份数据源**换三种展示。
我们 `Grid` 的公开方法只有：

```
column columns perPage actions batchActions batchAction
getBatchActions getCustomBatchActions toNodes toArray
```

**没有 `mode`**。所以「同一批数据，管理端看表格、用户端看卡片」现在得写两套前端。

**抄什么**：`Resource::gridMode('table'|'list'|'cards')`，前端三个渲染分支。

**估工**：2–3 人日（前端多两个渲染分支是主要工作量）。
**验证**：同一 Resource 三种 mode 各出一条 e2e 断言，断言渲染出的容器 class 不同、但行数相同。

---

### 抄 3：把「条件」抽象成统一对象

**为什么**：我们的 `visibleWhen(field, value)` 只支持**等值 / in 数组**：

```php
$form->select('priority')->visibleWhen('type', 'bug');
```

amis 支持任意表达式：`visibleOn: "${age > 18 && type === 'vip'}"`。
**但不要抄它的 JS eval** —— 那会让声明变得不可静态分析（我们最大的优势就没了）。

**抄什么**：抄**「条件对象」这个抽象**，而不是表达式引擎。
即：把目前的 `{field, value}` 扩成一个**受限条件词表**，例如
`whenEquals` / `whenIn` / `whenNotEmpty` / `whenGreaterThan`，可以 `and`/`or` 组合。
**保持可静态分析** —— 每个条件都还是一个声明，不是一段代码。

**为什么这条重要**：`Field.php` 的 `visibleWhen` 注释里记着一次**真实事故**：

> 实测代价：一个 LLM 为了做「选 A 显示 B」，翻遍 `llms.txt`、自省接口、
> **反射了 142 个框架类**，最后**自己写了一个扩展**：注册字段类型、手写 `visibleWhen()`、
> 注入一段 JS 去改 `hidden`。
> 也就是说：声明一句就该解决的事，变成了每个项目各自实现一遍。

**这条注释就是「AI 复杂度」的定量证据**：142 个类的反射，换来一句本该成立的声明。

**估工**：2–3 人日（条件词表 + schema + 前端判定 + 校验接入）。
**验证**：反例 —— 用一个现有词表表达不了的条件，确认 `ai:verify` 会**报错并给出可用的替代**。

---

### 抄 4：`crud` 的「复合组件」设计

**为什么**：amis 的 `crud` 一份文档 **6455 行**，因为它把
「数据源 + 查询表单 + 列配置 + 工具栏 + 批量操作 + 行操作 + 弹窗表单 +
拖拽排序 + 地址栏同步 + 动态列 + 总结行」**封成一个组件**。

**好消息**：这一块**我们其实不差**。`Grid` + `Form` + `actions` + `batchActions`
已经覆盖了它的大部分。真正缺的是**「静默失效」的补齐**（13 个死 prop）。

**抄什么**：抄它的**设计原则** ——
「常见页面模式」应该**一个声明搞定**，而不是让使用者/ AI 自己拼。

**具体动作**：把 13 个死 prop 逐个**接通或删除**（这是上一份报告的第 0 步）。

**估工**：已单列，2–3 人日。

---

### 抄 5：属性表自动生成（自省补齐）

**为什么**：amis 的**每份组件文档**都带三张自动生成的表：
**属性表 / 事件表 / 动作表**（`crud.md` 里分别是第 4393 / 4524 / 5332 行）。
它从 TypeScript 类型生成，所以**文档不会和实现脱节**。

**我们的现状**：`capabilities.json` **219753 字节 / 22 个顶层键**，字段类型、列选项、
校验规则都列了 —— **但缺「每个字段类型渲染成什么样」**。

**抄什么**：给每个字段类型补**渲染样例**（HTML 片段或缩略图），
让 AI 读自省结果时**能看到界面**，而不是盲写。

**估工**：2–3 人日。
**验证**：断言每个字段类型都有样例；且样例是**真实渲染产物**（不是手写文档）。

---

### 抄 6：主题编辑器思路

**为什么**：amis 有 `amis-theme-editor-helper` + `css-vars.md`（84 行），
把主题做成一等公民。

**我们的现状（这是个没做完的承诺）**：
`UI与基座方案.md` §5.4 承诺了 **3 套主题（墨玉/深空/极光）**，
但实测 `themes.css` 的选择器只有：

```
[data-mode="light"] [data-mode="dark"] @media (prefers-color-scheme: dark)
```

**没有 `data-theme` / `data-accent`** → **实际只发了一套蓝**。
（`design-system.css` 有 141 个 token，基础是好的。）

**抄什么**：两选一 ——
① 把承诺的 3 套主题**真的发货**（改 `data-theme` 切换）；
② 或做一个**主题导出**（把 token 暴露成 JSON，可粘贴替换）。

**估工**：① 1–2 人日（token 已有）；② 2–3 人日。

## 四、不该抄的 5 件（都有具体理由）

| 不抄 | 理由 |
|---|---|
| **React + mobx + lodash + moment + echarts + xlsx + exceljs + hls.js**（38 依赖 / 73.74 MB） | 与「零构建 + 1.0MB」直接冲突。要图表可以**单独**做一个轻量声明，不必背上 echarts 全家桶 |
| **JSON 作为编写语言** | 我们已经有 PHP。**PHP 有类型检查、IDE 补全、静态分析，JSON 没有**。这是升级不是妥协 —— 社区那篇文章的「各种乱码」正是 JSON 路线的代价 |
| **数据域 / 数据链**（`datascope-and-datachain.md` **533 行**） | amis 需要它，是因为它**纯前端**、要逐个组件配 `api` 取数。**我们的数据在后端 Resource 里统一出** —— 这是我们的优势，不必引入一套前端数据流 |
| **120 组件的大词表** | 那正是它「AI 学习成本高」的**原因**。照抄等于自毁我们最大的优势 |
| **可视化编辑器作为主入口** | 与「AI 写声明、人审阅」的定位冲突。可作**辅助**（如声明实验室），但不能成为主要使用方式 |

## 五、方案：分 4 批，每批独立可验证

按「对 AI 复杂度的贡献」排序，**不要并行做**（每批都会动 schema 产物，并行会互相冲突）。

### 批 1 —— 动作规范补全（**先做这个，纯后端**）

| 项 | 内容 |
|---|---|
| 做什么 | 13 个死 prop 二选一（接通 / 删除）+ `ai:verify` 对死 prop **事前拦截** + 新增 `cannotExpress` 段 |
| 为什么 | AI 现在无法预知哪些声明无效 —— 这是最大的一处复杂度 |
| 估工 | **2–3 人日** |
| 验证 | 反例：用 `->placeholder()` 声明，确认 `ai:verify` 报错并给出替代 |
| 参考 | 上一份报告（`固定前端换AI复杂度-方案分析.md`）的第 0 步 |

### 批 2 —— 页面级词汇（**抄 amis 的核心价值**）

| 项 | 内容 |
|---|---|
| 做什么 | `Resource::layout()` + 三种容器（`tabs` / `cards` / `sections`）；**补上 `Show` 的渲染方**；`gridMode('table'|'list'|'cards')` |
| 为什么 | 页面结构完全表达不了 → AI 只能写 Blade |
| 估工 | **5–8 人日**（含双端渲染 + e2e） |
| 验证 | ① 声明一个带标签页的详情页 → 两端渲染产物都有对应结构；② 同一 Resource 三种 `gridMode` 行数相同、容器不同 |
| 反例 | 先确认：不加 `layout()` 时，AI 表达同一需求需要写多少前端代码（记录基线） |

### 批 3 —— 条件词表 + 自省补齐

| 项 | 内容 |
|---|---|
| 做什么 | 把 `visibleWhen(field, value)` 扩成受限条件词表（可静态分析，**不做 JS eval**）；给每个字段类型补渲染样例 |
| 为什么 | 条件表达能力不足（有 142 类反射的真实事故）；AI 看不到界面 |
| 估工 | **4–6 人日** |
| 验证 | 条件词表：每个条件有反例（表达不了的必须报错）；样例：断言是真实渲染产物 |

### 批 4 —— 主题发货

| 项 | 内容 |
|---|---|
| 做什么 | 把承诺的 3 套主题真的发货（`data-theme` 切换），或做主题导出 |
| 为什么 | 这是文档里承诺过、实际没发的东西 |
| 估工 | **1–3 人日** |
| 验证 | 断言 3 个 `data-theme` 下的主色对比度都 ≥ 4.5（沿用已有的 72 项校验） |

**总计 12–20 人日。** 批 1 最便宜、收益最直接，建议先做它单独验证效果。

## 六、最大的风险：词表膨胀

**这是本方案唯一需要长期纪律的地方。**

amis 的 120 个组件不是一天长出来的。它每次都在解决一个真实需求，
最后变成 AI 学不会的规模。**我们抄它的结构词汇时，会走上同一条路。**

建议立一条**词表预算**（写进 `AGENTS.md`）：

> **新增任何词表项（字段类型 / 容器 / 列选项）必须同时满足三条：**
> 1. 有 `ai:verify` 能验证的**声明形态**
> 2. 有**渲染样例**进 `capabilities.json`
> 3. 有**至少一条 e2e 断言**证明它真的被渲染（不是"声明了但没渲染方"）
>
> **不满足第 3 条的，一律不许进词表。**

**为什么这条纪律是关键**：
本项目已经有过 **13 个死 prop** 和 **一个没有渲染方的 `Show`**。
它们的共同成因就是：**加声明比加渲染容易**。
不加约束的话，词表越大，**"声明了但不生效"的面积越大** —— 而 AI 恰恰最依赖声明可信。

## 七、我的整体判断

**amis 是一份很好的"反面参照 + 正面素材"：**

- **反面参照**：它证明了「大词表 + JSON + 纯前端」这条路会让 AI 学不会 ——
  社区不得不为此外挂 MCP server、Claude Skill、双 Agent 和 JSON 验证层。
  **我们已经走在更好的路上，不要回头。**

- **正面素材**：它的**页面级结构词汇**（容器即 schema）、**`mode` 切展示**、
  **复合组件**、**属性表自动生成**、**主题编辑器** —— 这 5 个思路
  恰好补在我们的空白处，而且**都可以小规模落地**，不必背上它的 73 MB。

**所以我的建议是**：
> **抄 amis 的"结构"，别抄它的"规模"和"实现"。**
