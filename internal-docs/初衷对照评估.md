# 初衷对照评估报告

> 评估日期：2026-10-11 · 评估对象：Aimanong v1.6.1
> 方法：以 `internal-docs/方案.md`（原始设计）与 `开发计划.md`（北极星指标）为标尺，
> 逐条对照当前代码、提交历史与验证记录。**所有结论都给出可复现的证据出处。**

---

## 结论摘要

| 问题 | 结论 |
|---|---|
| 初衷是什么 | 做**专给 AI Agent 用的后台框架**，卖点是「让 AI 一次写对」 |
| 是否在预期轨道上 | **主体在轨**。四大设计哲学全部落地，AI 能力层是真实差异化 |
| 有没有走偏 | **有 3 处实质性偏离**，另有 4 处「承诺与现状不符」 |

**最需要正视的一条**：项目最重要的指标——**AI 一次成功率**——已经
**整整两个大版本（v1.5.0 / v1.6.0）没有测量过**。而这两个版本
恰好是改动量最大的阶段（UI 重做 21 个提交 + 六项基座 10 个提交）。

## 一、初衷是什么

原始文档里写得非常明确，三句话可以概括：

### 1. 核心命题（`方案.md` §1）

> **「AI 优先」不是"文档写好一点"，而是架构层面的重新设计。**
>
> 人要的是：优雅的抽象、灵活的扩展、渐进式的学习曲线。
> AI 要的是：**低歧义、可自省、可验证、错误可自愈、无需记忆大量上下文。**
>
> **在「AI 优先」的设计里，我们明确牺牲"灵活性"换取"确定性"。**

### 2. 解决的四大痛点（`方案.md` §1.1）

| 痛点 | 解法 |
|---|---|
| 不知道有什么 | 自省 API |
| 不知道怎么用 | 单一规范签名 + Schema 即文档 |
| 不知道错在哪 | 可自愈错误（didYouMean + 示例） |
| 改了不知道对不对 | `ai:verify` 生成后自动校验 |

### 3. 北极星指标（`开发计划.md` §7）

> **AI 一次成功率** —— 本项目所有技术决策最终都向这个指标看齐。
>
> - L1 简单 ≥ 95% / L2 中等 ≥ 85% / L3 复杂 ≥ 70%
> - 每轮用 Claude / GPT / DeepSeek / 通义各跑一遍，**只看最低值**
> - **每月一次全量回归 + 每次发版增量回归**
> - 结果公开在文档站（"这是最强的营销素材，也是诚实的质量承诺"）

**注意最后两条**：这是项目自己对用户的承诺 —— 每次发版都要增量回归。

## 二、在轨的部分（做得对的）

### ✅ 2.1 四大设计哲学全部落地可验证

| 哲学 | 落地证据 |
|---|---|
| **Schema 是唯一真相** | 一份 PHP 声明 → 4 份产物；`aimanong:schema --check` 漂移检测可阻断 CI（实测 `✅ 全部产物与声明一致`） |
| **零隐式魔法** | 全仓库只有 1 处 `__call`（`Form::Form.php:230`），且**只服务已注册类型**，未注册抛异常并列出可用类型 |
| **错误即教学** | 5 个可自愈异常类：`GhostColumnException` / `DictNotFoundException` / `InvalidQueryColumnException` / `UnknownFieldTypeException` / `AiReadableException` |
| **可自省** | `/__ai/` 5 个接口 + MCP 8 个工具，且 `capabilities.json` 已含 `foundation`（7 项）与 `dictionaries`（10 个字典） |

### ✅ 2.2 「五层设计」五层齐全

| 层 | 落地 |
|---|---|
| L1 `llms.txt` | 261 行，已补 v1.6.0 新能力写法 |
| L2 `AGENTS.md` | 79 行 |
| L3 自省 API | `IntrospectionController` + 5 个路由 |
| L4 MCP Server | 8 个工具（含 `search-docs` —— 第五轮实测证明这是 AI 的主力发现路径） |
| L5 可自愈错误 | 见上 |

### ✅ 2.3 北极星指标确实被认真执行过（前五轮）

`AI实测记录.md` 记录了一条**非常诚实**的曲线：

| | 第 1 轮 | 第 2 轮 | 第 3 轮 | 第 4 轮 |
|---|---|---|---|---|
| 一次成功率 | 0.5 | 0.5 | **1.0** | **1.0** |

而且第一轮**主动从 1.0 下调为 0.5**：

> **首版记录误判为 1.0，原因是只看了最终产物的正确性，没有追溯过程。**

这种自我纠错的态度，是项目最宝贵的资产之一。

### ✅ 2.4 真实场景验证形成了方法论并抓到了真问题

三次真实场景验证（电商 → 插件 → CRM），累计抓到的都不是表面问题：

- 电商：关联列 + 条件高亮**完全缺失**（前五轮 AI 实测全没暴露）
- 插件：字段类型硬编码、Form 无分发入口
- CRM（本次）：4 个「界面看着正常、测试全绿」的缺陷

## 三、偏离的部分（需要正视）

### ⚠️ 偏离 1：北极星指标停测两个大版本 —— **最严重**

**事实**：

```
AI实测记录.md 最后一轮日期：2026-10-09（第五轮）
之后发布的版本：v1.3.0 / v1.4.0 / v1.4.1 / v1.5.0 / v1.6.0 / v1.6.1
```

`开发计划.md` 明确承诺「**每次发版增量回归**」，但 v1.5.0 与 v1.6.0
**没有任何 AI 一次成功率的测量记录**。而这两个版本是改动最大的：

| 区间 | 提交数 | 内容 |
|---|---|---|
| v1.4.1..v1.5.0 | **21** | 全站视觉重做 |
| v1.5.0..v1.6.1 | **10** | 六项基座 + CRM 验证 |

**为什么这是最严重的偏离**：

一个「专给 AI 用的框架」，如果不再测量「AI 用起来顺不顺」，
那它是否还配得上这个定位，就**失去了唯一的客观依据**。
UI 好不好看可以看图，但「AI 是否能一次写对」只能靠测量。

**而且有具体风险未被覆盖**：v1.6.0 新增了 7 项能力
（`readonly` / `dict` / 上传四件套 / `requiredOnCreate` / `omitWhenEmpty` /
`relation` / 个人中心），这些都需要验证「AI 能否自主发现并正确使用」——
第五轮的结论（`search-docs` 是主力发现路径）**对新能力尚未复验**。

### ⚠️ 偏离 2：端到端测试形同虚设，且未随新能力扩展

**事实**：

仓库里**本来就有** `tests/e2e/framework-e2e.php` 与 `http-e2e.php`，
本次实测 `framework-e2e` 依然 **27/27 通过**。

但是：

```
=== e2e 是否覆盖 v1.6.0 新基座能力 ===
operation-log: 0
login-log: 0
dict: 0
upload: 0
profile: 0
admin-user: 0
readonly: 0
```

**并且它默认被跳过**：

```
【6】端到端测试
  ⚠️  跳过端到端（加 --with-e2e 启用，需 demo 环境）
```

`pre-release.sh` 里写的是「demo 服务未运行则跳过」——
**这是一条会把失败伪装成通过的路径**。CI 里 (`ci.yml`) 也只跑
Pint / PHPStan / PHPUnit，**不跑 e2e**。

这正好解释了本轮 CRM 验证为什么会抓到 4 个缺陷：
它们全都逃过了「编译 + 单测 + 27 项 e2e」三道关。

### ⚠️ 偏离 3：分支纪律从 v1.3.0 起失效

`AGENTS.md` 第 47 行白纸黑字：

> ❌ 直接在 `main` 上开发（走 `feat/*` 分支 + PR）

实际：

```
feat/m5-enhancements   最后提交 2026-10-09   ← 分支纪律在此终止
fix/ai-test-findings   最后提交 2026-10-09
fix/round4             最后提交 2026-10-09
main                   最后提交 2026-10-11   ← 之后全部直接在 main
```

v1.3.0 之后的 **40+ 个提交全部直接落在 main**，无 PR 无 review。
项目是 AI 主导开发，人类的 review 环节本就更重要 —— 这条纪律的失效
意味着**人类审阅者的参与度实际降到了零**。

## 四、承诺与现状不符（4 处）

这类问题的危害在于：**对一个「可自省、可验证」为卖点的框架，
自身对外声明失真会直接破坏信任基础。**

### ❌ 4.1 OpenAPI 仍为只读资源宣告写接口 —— **违反第一原则**

v1.6.0 新增了只读资源能力（`Resource::readonly()`），接口层实测返回 403：

```json
{"message":"「操作日志」是只读资源（Resource::readonly() 返回 true），只能由系统写入"}
```

但生成的 OpenAPI **仍然宣告了 POST / PUT / DELETE**：

```
只读资源的 OpenAPI 路径：
  GET    /admin/admin-login-logs
  POST   /admin/admin-login-logs      ← 实际 403
  PUT    /admin/admin-login-logs/{id} ← 实际 403
  DELETE /admin/admin-login-logs/{id} ← 实际 403
  （admin-operation-logs 同样）
```

**这正是 `方案.md` 第一条要杜绝的事**：

> **Schema 是唯一真相** …… **杜绝文档与实现漂移——这是 AI 出错的最大来源。**

`OpenApiEmitter` 完全没有感知 `readonly`（grep 结果：0 处）。
AI 若照 OpenAPI 写代码，会写出必然 403 的调用。

**同类缺口**（同一根因，需一并查）：

| 产物 | `readonly` | `upload` |
|---|---|---|
| schema.json | ✅ 有 | ✅ 有 |
| types.ts | ❌ 无 | ❌ 无 |
| openapi.json | ❌ 无 | ❌ 无 |
| ai-context.md | ❌ 无（0 处提到"只读"） | ❌ 无 |

四个 emitter 的能力覆盖不一致，而 `EmittersTest` 只断言了
「字段数量一致」（`test_all_emitters_agree_on_field_count`），
**没有断言能力标志一致**。

### ❌ 4.2 README 描述了两个不存在的目录

```markdown
| `packages/ui` | Vue 3 组件库（npm: `@aimanong/ui`） |
| `demo/`       | 示例项目 |
```

实际：

```
packages/ui  存在，文件数=1   → 只有 packages/ui/src/.gitkeep
demo         存在，文件数=1   → 只有 demo/.gitkeep
packages/ui 无 package.json   → 尚未发布到 npm
```

而前端实际是**单文件内联 Vue**（`resource.blade.php` 944 行 +
`profile.blade.php` 302 行），并没有使用 `packages/ui`。

这不是错误决策（零构建内联是合理取舍），但 **README 不该这么写**。

### ❌ 4.3 Playground 的能力落后于框架

`docs/public/playground/compiler.js` 是**真实解析器**（不是硬编码演示），
但它的 DSL 解析范围停在 v1.4 前后：

| 对比项 | Playground | 框架实际 |
|---|---|---|
| 字段类型数 | **26** | **31** |
| 缺哪几种 | `image` / `images` / `file` / `files` | — |
| `->dict()` | ❌ 不支持 | ✅ |
| `->requiredOnCreate()` | ❌ 不支持 | ✅ |
| `->omitWhenEmpty()` | ❌ 不支持 | ✅ |
| 资源级 `readonly()` | ❌ 不支持 | ✅ |

（注：Playground 里的 `readonly` 是**字段级** `->readonly()`，与
v1.6.0 的**资源级** `Resource::readonly()` 不是一回事；
`image` 也只作为**列展示器**存在，没作为表单字段类型。）

README 把它列为卖点（"浏览器里改 Resource 声明，实时看四份产物"），
但用户试 `$form->image('cover')` 或 `->dict('order_status')`
都不会得到正确产物 —— 而这是潜在用户**接触框架的第一站**。

### ❌ 4.4 「一次成功率 1.0」的宣传需要重新校准

`README.md` 第 33 行：

> **v1.0.0 已发布** —— 全部里程碑（M0–M6）完成，经过 5 轮 AI 实测、累计修复 20 个真实缺陷。

数字本身没问题。但**第五轮之后又发现了至少 10 个真实缺陷**（其中
2 个是框架级：多对多写入从未生效、只读资源 OpenAPI 漂移）。
「1.0」的可信度在一个「多对多关联写入从未生效」的框架上，
需要用新一轮实测重新确认。

## 六、根因分析

三个偏离不是孤立的，指向同一个根因：

> **项目从「AI 优先」的验证驱动，滑向了「功能优先」的交付驱动。**

具体表现：

| 阶段 | 驱动力 | 验证方式 |
|---|---|---|
| v1.0.0 ~ v1.2.0 | **指标驱动** | 每个里程碑都跑 AI 实测，结果公开 |
| v1.3.0 之后 | **功能驱动** | 改为「真机点一遍 + 单测 + PHPStan」 |

这个转向有合理的触发点（v1.3.0 定位调整为「带地基的平台」，
功能面变大、AI 实测成本上升）。但**代价没有被显式记录**：

- 不再有「AI 能否一次写对」的客观数据
- e2e 覆盖没跟上（新增 7 项能力，e2e 覆盖 0 项）
- 分支/review 纪律失效，人类审阅环节消失

值得肯定的是：**真实场景验证（CRM）部分补上了验证缺口** ——
它确实抓到了 4 个真问题。但它验证的是「功能能不能用」，
**不是**「AI 能不能用对」。这两个是不同的问题。

## 七、建议（按优先级）

### P0 · 立即做（成本低、直接挽回核心承诺）

1. **补一轮 AI 实测，覆盖 v1.6.0 新能力**
   - 至少 L2 级别，重点测**能力发现**：用业务语言描述需求
     （如「跟进记录要能传附件」），看 AI 能否自主发现 `->files()`
   - 参考第五轮方法：**禁止读源码**，只允许 `/__ai/*` + MCP
   - 结果写入 `AI实测记录.md`，无论好坏

2. **修 OpenAPI / types.ts / ai-context.md 的 readonly 与 upload 漂移**
   - 并给 `EmittersTest` 加一条**能力标志一致性**断言
     （防止将来再漂）

3. **让 e2e 覆盖新基座能力，并让 CI 真正跑它**
   - 当前 e2e 是可跳过的、CI 不跑的 —— 等于没有
   - 最低要求：`pre-release.sh` 里 demo 未运行应**报错**而不是跳过

### P1 · 修正对外表述

4. README 修正 `packages/ui` 与 `demo/` 的表述（要么补齐，要么删掉）
5. Playground 的 `FIELD_TYPE_MAP` 补齐 4 种上传类型
6. README 的「5 轮实测 20 个缺陷」补上第五轮之后的数据

### P2 · 恢复工程纪律

7. 恢复 `feat/*` 分支 + PR，**尤其是 AI 主导开发时，人类 review 不能省**
8. 把「端到端跑一遍并核对落库」写进发版清单（本次 CRM 教训）

## 八、总体评价

**这个项目的主体没有走偏。** 它的核心差异化——自省 API + MCP +
Schema 单一真相 + 可自愈错误——是**真实存在且经过验证的**，
不是 PPT 卖点。前五轮 AI 实测的 0.5 → 1.0 曲线，
以及三轮真实场景验证抓到的框架级缺陷，都说明这套方法论是有效的。

**但有 3 处实质性偏离，其中 1 处触及根本**：

- 北极星指标停测两个大版本 —— 对一个以「AI 用得好不好」为卖点的框架，
  这是**丢了唯一客观依据**
- e2e 形同虚设且未随新能力扩展
- 分支与 review 纪律失效

**最需要说的一句**：

> 项目现在有能力回答「这个框架功能全不全」，
> 但暂时**没有能力回答「AI 用它顺不顺」**。
>
> 而后者才是当初做这个项目的理由。

好消息是：补救成本不高（一轮实测 + 两条断言 + 一个 CI 步骤），
且项目已有的验证方法论（禁止读源码、只看最低值、父 Agent 独立核验）
完全可以复用。
