# 发布前验证流程

> 每次发版前必须走完。**这不是形式主义，是踩坑记录的制度化。**

---

## 为什么需要这套流程

v1.0 的开发过程反复证明一件事：**纸面测试发现不了真实问题。**

| 验证方式 | 发现的问题 | 数量 |
|---|---|---|
| 单元测试（98 项） | 逻辑缺陷 | — |
| **AI 实测**（5 轮） | 框架纠错能力缺陷 | 20 个 |
| **真实场景验证** | 能力覆盖缺口 | 2 个能力 + 4 个 bug |
| **官方插件开发** | 扩展机制缺口 | 2 个机制缺口 + 1 个前端 bug |

**关键数据**：真实场景验证发现的 2 个能力缺口（关联列、条件样式），
**在前五轮 AI 实测中完全没暴露** —— 因为那些任务都是单表、无业务规则的 CRUD。

**结论：四种验证方式互补，缺一不可。**

## 一、基础门禁（自动化，必须全绿）

```bash
cd packages/framework
./vendor/bin/phpunit          # 单元测试
./vendor/bin/phpstan analyse  # Level 8 静态分析
./vendor/bin/pint --test      # 代码风格
```

| 项 | 通过标准 |
|---|---|
| PHPUnit | 0 failures / 0 errors |
| PHPStan | `[OK] No errors`（Level 8） |
| Pint | `PASS` 全部文件 |

**再加 CI**：push 后确认 GitHub Actions 全绿（含 PHP 8.2 兼容性 job）。

---

## 二、端到端验证（需 demo 环境）

```bash
# 启动 demo 服务
cd <demo-app> && php artisan serve --port=8899

# 1. 框架功能（27 项，不需 HTTP）
php tests/e2e/framework-e2e.php

# 2. HTTP 层（20 项，需服务运行）
php tests/e2e/http-e2e.php
```

| 项 | 通过标准 |
|---|---|
| framework-e2e | 27/27 |
| http-e2e | 20/20 |

**覆盖**：多应用隔离、树形、导出、分步表单、AI 自省接口、资源安全。

## 三、AI 实测（验证「AI 能否顺畅使用」）

### 目的

验证框架的**纠错能力**，而非功能是否存在。

### 执行方式

1. 启动一个**完全不了解框架**的 AI Agent
2. 只给三样东西：文档站地址、MCP 连接、业务需求
3. **禁止读框架源码**（明确写进任务）
4. **零人工提示**
5. 复核者**独立复现** AI 的每个结论（不轻信自述）

### 评分标准

| 结果 | 得分 |
|---|---|
| 一次生成即可运行，`validate_declaration` 全绿 | 1.0 |
| 需 1 次修正（读错误信息后自行改对） | 0.5 |
| 需 ≥2 次修正，或需人工介入 | 0 |

**关键指标——框架纠错贡献**：AI 出错后，是**框架的错误信息**帮它改对的，
还是自己读源码/靠经验猜的。

### 通过标准

| 难度 | 目标 |
|---|---|
| L1 简单 | ≥ 95% |
| L2 中等 | ≥ 85% |
| **框架纠错贡献** | **100%**（不达标说明 API 设计有问题，应回炉） |

### ⚠️ 重要约束

**不要在 AI 实测进行中修改框架。**

v1.0 期间犯过这个错：AI 报告"框架在会话进行中被修改，
同一文件 21:08 测 500、21:14 测 200"——导致它早期的探测结论失效。

**正确做法：实测期间框架冻结，实测结束后统一修复。**

## 四、真实场景验证（验证「能力覆盖度」）

### 目的

用**真实业务复杂度**暴露"示例场景看不出"的缺口。

### 执行方式

1. 设计**贴近真实业务**的数据结构
2. 需求用**业务语言**描述，**不指定 API 名**
3. **刻意混入"客户想要但可能做不到"的诉求**
4. 要求 AI 如实报告：哪些支持良好、哪些别扭、哪些做不到

### 场景设计要点

| 维度 | 示例场景 | 真实场景（必须覆盖） |
|---|---|---|
| 数据关系 | 单表 | **多表外键关联** |
| 业务规则 | 无 | **状态机、阈值告警** |
| 字段数 | 5–10 | **13–16** |
| 展示要求 | "显示这个字段" | **"要能一眼看出来"** |
| 边界情况 | 无 | **软删除、JSON 字段、空值** |

### 通过标准

| 项 | 标准 |
|---|---|
| 需求满足率 | ≥ 90% |
| **无法实现的需求** | **必须如实上报，不得静默妥协** |
| 发现的框架缺口 | 全部记录并评估是否修复 |

### v1.0 的实战结果

19 项需求 / 17 项支持 / **2 项暴露能力缺口**（关联列、条件样式）——
均已修复。

## 五、插件验证（验证「扩展机制可用性」）

### 目的

用**真实插件**验证插件机制 —— 而不只是测"能加载"。

### 执行方式

选一个**真实有需求**的扩展开发现（不是玩具示例）：

| 候选 | 验证维度 |
|---|---|
| 省市区选择器 | 注入字段类型、自带数据与路由 |
| 富文本编辑器 | 前端资源集成 |
| 对象存储上传 | 替换核心行为 |

### 检查项

| 项 | 通过标准 |
|---|---|
| 独立发包 | `composer require` 即可用，不改框架核心 |
| 注入字段类型 | `$form->xxx()` 可用，且编译产物正确 |
| 注册路由 | 挂在正确的后台前缀下 |
| **失败隔离** | 插件出错不拖垮框架与其它插件 |
| 未注册方法 | 抛明确异常 + 可用列表（**不是任意魔法入口**） |

### v1.0 的实战结果

写 `aimanong/region` 时暴露 **2 个机制缺口**（字段类型硬编码、Form 无方法入口）
+ **1 个前端 bug**（新增弹窗未初始化插件字段状态）。

> **这些在写真实插件之前完全不知道存在。**

| 组 | 检查项 |
|---|---|
| 版本号 | composer.json / `Aimanong::version()` / CHANGELOG / README 徽章 四处一致 |

| 命名一致性 | 无残留旧项目名 |
| CI 配置 | ci.yml + deploy-docs.yml |
| 文档站 | `npm run build` 成功 |

## 八、从实践中提炼的四条原则

### 原则 1：修之前先全量审计

AI 报告的问题往往是**表层症状**，根因常比报告更广。

> 实例：AI 报告 1 个关联搜索 500，
> 审计后发现 **3 处同类风险** + **1 个静默失败**（不存在的列被放过）。

### 原则 2：校验器必须可被证伪

**别信"绿灯"** —— 要能独立验证"绿灯是否可信"。

> 实例：AI 发现给外键加 `searchable()` 就能骗过校验器，
> 但客户要的是按商品名搜索，实测返回 0 条。
>
> **校验器只验"列名在不在"，不验"搜的是不是业务字段"。**

### 原则 3：声明能编译 ≠ 功能可用

三层验证缺一不可：

1. `validate_declaration` + `requirements` → 需求是否达标
2. 读 `schema.json` → 声明是否真编译进去
3. **实际请求 API / 打开页面** → 是否真的生效

> 前两层全绿都不代表功能可用。

### 原则 4：实测期间框架冻结

并发修改会让 AI 的探测结论失效，且难以判断问题归属。
**串行执行：实测 → 收集问题 → 统一修复 → 再实测。**
