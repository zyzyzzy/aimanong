# 用「固定前端」换「AI 复杂度」—— 判断与方案

> 2026-10-16 · 针对「给 AI 码农定制一套有鲜明特点的前端，让 AI 不必关心前端实现细节」这一构想
>
> 结论基于代码实测与端到端复现，不是推理。每条结论都标了证据来源。

---

## 〇、判断先行

你的构想里有**两个命题**，一个对一个不对，而它们被绑在了一起：

| 你的命题 | 我的判断 | 理由（一句话） |
|---|---|---|
| **A.「有鲜明特点的前端」→ 极大降低 AI 复杂度** | ❌ **不成立** | 「视觉身份」与「AI 复杂度」之间**没有因果关系** —— AI 根本不看界面 |
| **B.「前端规则完全进入 AI 可知范围」→ AI 不必关心前端细节** | ✅ **完全成立**，而且这是本项目最该做的一件事之一 | 它直接就是宪法①（AI 优先）+ ③（零隐式）的落地 |

**但 A 里包着一个对的东西，被"鲜明特点"这个说法盖住了：**

> 真正有价值的不是「鲜明」，是**「固定」**。
>
> **只有渲染结果是固定的，才可能对渲染做自动化断言。**
> 而今天唯一的门禁是「**静态扫字符串** `props.X` 有没有出现过」——
> 它**验不了「接得对不对」**。这就是 13 个死 prop 能长期存活的原因。

所以我的建议是：**做，但把目标从"有特点"改成"契约化"**。
「有特点」会是副产品（自研封闭组件集自然观感统一），不该是目标。

## 一、先看一个端到端复现：AI 的意图是怎么消失的

我造了一个只加了一行声明的 Resource，跑了一遍真实链路：

```php
// App\Aimanong\PlaceholderProbeResource
public static function form(Form $form): void
{
    $form->text('name')->label('名称')->placeholder('请输入部门名称');
}
```

**① `ai:verify` 通过** —— 声明语法完全合法
**② `/__ai/schema/placeholder-probe` 下发了**：

```json
{"name": "name", "type": "text", "label": "名称",
 "props": {"placeholder": "请输入部门名称"}, "rules": []}
```

**③ 页面 HTML 里搜「请输入部门名称」→ 出现 `0` 次。**

三个环节全部"正常"，**只有最后一步静默丢掉**。
`resource.blade.php` 里只有两个 `placeholder=`（搜索框、筛选框），**没有 `props.placeholder` 的读法**。

**这就是你说的痛点的精确形态**：
AI 写的代码**看起来对、校验通过、schema 里也有** —— 但界面上什么都不发生，而且**没有任何机制告诉它**。
结果就是：AI **必须**知道「`placeholder` 是 13 个死 prop 之一」这种**前端实现细节**。

### 13 个死 prop 的完整清单（框架自己在 `Capabilities::unwiredProps()` 里承认的）

| prop | 用户看到的后果 |
|---|---|
| `placeholder` | 占位文案不出现 |
| `min`（number） | 最小值不下发到 input |
| `width`（column） | 列宽不生效 |
| `format`（dateTime） | 时间格式写死 `slice(0,19)` |
| `symbol`（money） | 界面不显示货币符号（**导出侧读了** → 两端分叉） |
| `decimals`（money） | 固定两位小数，声明无效 |
| `text`（link） | 链接文案写死「打开 ↗」 |
| `height`（image） | 图片高度不生效 |
| `separator`（tags） | 分隔符不生效 |
| `allowHalf`（rate） | 半星选择无效 |
| `display` | 只读展示不按此渲染 |
| `disk` | 上传盘只取 config |
| `relation` | 显式声明是空操作（只认列名里的点号） |

**这 13 个，就是"AI 不得不关心前端"的全部来源**（在字段层面）。

## 二、你的直觉里，哪一部分是真正对的

你说「越是灵活的东西，复杂度就越大」——**这句话本身是对的**，而且框架已经吃到了它的红利。

对比一下「AI 做后台界面」的两条路：

| | 传统前端（React + Tailwind） | Aimanong 现在的路 |
|---|---|---|
| AI 要写的 | 组件树 + 状态 + 样式 + 路由 | **一个 PHP Resource 声明** |
| 可表达的界面数 | 无限（也就意味着无限出错方式） | **30 个字段类型 × 封闭列选项** |
| AI 要知道的 | 极多 | 少 |

**所以"用约束换复杂度"这条路，框架已经在走了，而且走得比大多数框架远。**
你不是在提一个新方向，你是在**指出这条路还没走完**。

**那没走完的部分在哪？** 我实测了三处：

### 缺口 1：词表会撒谎（13 个死 prop）

见上。**这是最大的一处**，因为 AI 无法预知。

### 缺口 2：词表有洞（有些 UI 需求表达不了）

`FieldType` 注册表 **30 个类型**，实测清单：

```
text textarea email url password tel number decimal money rate slider
select multiselect radio checkbox switch date datetime time daterange
image images file files color icon tags hidden display divider
```

**AI 常见的需求里，这些表达不了**（我按实际项目常见度排）：

| 需求 | 词表里有没有 | 现在 AI 只能 |
|---|---|---|
| **富文本 / HTML 内容** | ❌ **没有** | 写插件的 `fieldView` + blade（= 关心前端） |
| **图表 / 报表可视化** | ❌ 没有 | 同上 |
| **主子表**（订单 + N 行明细） | ❌ 没有嵌套表单 | 同上 |
| **地图选点** | ❌ 没有 | 同上 |
| **代码编辑器** | ❌ 没有 | 同上 |
| 自定义仪表盘 | ❌ **没有声明机制** | **改框架的 `index.blade.php`**（实测那些统计卡就是手写 Blade） |

### 缺口 3：AI 看不到界面

`capabilities.json` 有 **219KB / 22 个顶层键**，把字段类型、列选项、校验规则全列了 ——
但它**全是 JSON 文本**。AI 读完知道"有 `money` 类型"，**不知道它长什么样**。

→ 这在"AI 做界面"这件事上是真实信息缺失：
AI 是在**盲写 UI 声明**，写完只能等人打开页面看。

## 三、所以「鲜明特点的前端」到底该不该做

### 我原来（上一份报告）的判断要修正

上一份报告我说"不要做视觉身份迭代"，理由是**边际收益递减**（已做 6 轮）。
**那个判断在"好看"这个目标下成立，但在你这个新目标下不完整** ——
因为我现在发现了第三件事：

> **一个固定的前端，是"渲染可断言"的前提。**

今天为什么 `placeholder` 能死掉？因为门禁只能扫字符串：

```
PropConsumerTest：扫模板里有没有出现 "props.placeholder" 这个字符串
                 ↓
                 有 → 通过（但不保证接对了）
```

如果前端是**固定的组件契约**（每个字段类型有确定的 DOM 结构与 prop→属性映射），
就可以断言：

```
渲染契约门禁：渲染 → 取 DOM → 断言 input[placeholder] === 声明值
```

**到那时，"声明了但没渲染"这类问题在 CI 阶段就不可能出货。**

### 修正后的结论

| 说法 | 判断 |
|---|---|
| 「做一套鲜明特点的前端」 | ✅ 可以做，但**它是手段不是目标**，而且**它不是第一步** |
| 「有特点 → 降低 AI 复杂度」 | ❌ 顺序错了。**先修词表，再固化渲染，特点自然出现** |
| 「前端规则进入 AI 可知范围」 | ✅ **这才是主线**，且大部分是**后端/契约工作**，不是前端工作 |

---

## 四、方案：三步，按"对 AI 复杂度的贡献"排序

### 第 0 步 —— 让词表不再撒谎（**收益最大，且几乎不碰前端**）

| 做什么 | 具体 | 为什么排第一 |
|---|---|---|
| **13 个死 prop 二选一** | 能接通的接通（`placeholder` / `min` / `width` / `format` 都是几行改动）；接不通的**从 API 上删掉** | **删掉也是一种降复杂度** —— AI 少一个可以猜错的东西 |
| **`ai:verify` 事前拦截** | 用了死 prop → **立刻 422 并给出替代写法**，而不是"事后去 capabilities 里查" | 把"AI 必须知道"变成"AI 会被告诉你" |
| **新增 `cannotExpress` 段** | 明确列出"词表做不到什么 + 逃生口怎么走"。现在 `cannotVerify()` 只讲后端安全，没有前端表达力这一块 | 让边界进入 AI 可知范围 |

**这一步行完，你那句"AI 不用关心前端实现细节"就成立了 80%。**
而且它**不改一行前端代码**，风险极低。

### 第 1 步 —— 把渲染变成契约（**这一步才需要"固定前端"**）

| 做什么 | 说明 |
|---|---|
| **定义渲染契约** | 30 个字段类型 × 关键 prop → 确定的 DOM 结构 + 属性映射表（可以就是一份 JSON） |
| **加渲染门禁** | 每个被声明的 prop，必须真的出现在渲染产物里（DOM 级断言，不是字符串扫描） |
| **补上词表的洞** | 按优先级补：**富文本**（CMS 必需）→ 主子表 → 图表。补一个，AI 就少写一次前端 |

**这一步必须先"固定"才能做** —— 这就是你说的"鲜明特点的前端"的**真实价值所在**：
不是因为好看，而是因为**只有它不再变，才能对它写断言**。

> ⚠️ 时机上现在刚好：前端刚经历 6 轮迭代，结构已经稳定（2016 行设计系统 + 141 token）。
> 如果还是每周换配色，这一步做不了。

### 第 2 步 —— 把界面纳入 AI 可知范围（**你构想的核心，放最后是因为依赖前两步**）

| 做什么 | 说明 |
|---|---|
| **`/__ai/preview/{uri}`** | 返回该 Resource 的**渲染快照**（HTML 片段或缩略图），AI 能"看到"自己声明的结果 |
| **capabilities 带字段样例** | 每个字段类型的渲染样例，让 AI 读 JSON 时就知道"money 长这样" |
| **声明实验室**（上一份报告建议的） | 改声明 → 实时看四产物 + 渲染效果 + 校验结果。**人审阅用**，也是 AI 的反馈回路 |

**做完这三步，"前端规则完全融合到 AI 可知范围内"才真正成立。**

## 五、我对你这个想法的整体评价

**方向对，但把"手段"当成了"目标"，而且顺序反了。**

- 你说的问题（AI 不该关心前端细节）**真实存在**，我复现了：一行合法声明，界面上凭空消失。
- 但你给的手段（做有特点的前端）**解决的不是这个问题** ——
  6 轮配色迭代对 AI 复杂度的贡献是 **0**，因为 AI 不看界面。
- 而你的手段里**藏着正解**：「固定」。
  **只有固定，才能断言；只有能断言，声明才不会撒谎；声明不撒谎，AI 才不用关心实现。**

所以我的建议是：

> **不要先做前端。先做"不撒谎的词表"（第 0 步，几天，纯后端）。
> 然后做"可断言的渲染契约"（第 1 步）—— 那一步会自然要求前端固定下来。
> 最后把界面反向喂给 AI（第 2 步）。**
>
> 而你本来想要的"鲜明特点"，会在第 1 步结束时**作为副产品出现**：
> 一个自研的、封闭的、统一的组件集，观感天然区别于 Ant Design / Element 拼出来的后台。

## 六、成本与风险（诚实评估）

| 步骤 | 估工 | 风险 |
|---|---|---|
| 第 0 步：13 个 prop + verify 拦截 + cannotExpress | **2–3 人日** | 低。纯后端，有现成门禁（`PropConsumerTest` / `AiCapabilitiesTest`）可扩展 |
| 第 1 步：渲染契约 + 门禁 + 补词表洞 | **5–8 人日**（契约 2、门禁 2、富文本 1–2） | 中。需要前端稳定；补富文本会引入一个第三方编辑器 → 与"零 CDN"约束冲突，需选型 |
| 第 2 步：preview 接口 + capabilities 样例 + 声明实验室 | **4–6 人日** | 中低。接口现成（`/__ai/*` 实测全 200），但要处理生产环境 token 守卫 |

**总计 11–17 人日**，分三批交付，每批都能独立验证。

### 三个必须提醒的点

1. **第 0 步里"删 API"要谨慎** —— `placeholder` / `width` 这类，用户可能已经在用（哪怕无效）。
   删要有 deprecation 期；更好的做法是**先接通**（多数只是几行），实在不行的才删。
2. **富文本编辑器与"零 CDN"约束冲突** —— 需要选一个能本地化的（体积会显著增加，可能是当前前端资产的数倍）。这是第 1 步最大的未知。
3. **第 1 步的渲染门禁要有反例验证** —— 按项目惯例（`AGENTS.md`：门禁自身必须做反例验证），
   必须先造一个"故意不渲染的 prop"确认门禁会红，才能相信它。
