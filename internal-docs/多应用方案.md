# 多应用（多后台）方案

> 日期：2026-10-15
> 状态：**待确认** —— 先确认我理解对了再动手

---

## 一、我先说我的理解（这是最需要你确认的部分）

你要的是：

```
一个项目里，同时跑多个「后台」，它们互相独立：

  /admin      总管理后台     运营人员用，能看全部数据、配全部东西
  /user       普通用户后台   普通用户用，只看自己的东西
  /agent      代理商后台     代理商用，看自己名下客户的数据

每个后台：
  · 有自己的登录页（账号体系独立：管理员 ≠ 用户 ≠ 代理商）
  · 有自己的菜单（用户后台不该看到「管理员账号」「操作日志」）
  · 有自己的权限（同一个 Resource 在不同后台的权限是分开的）
```

### ⚠️ 这里有一个**容易混淆的点**，我先说清楚，免得做错方向

「多应用」和「多租户」是**两件事**，我理解你要的是**多应用**：

| | 多应用（我理解你要的） | 多租户（另一个东西） |
|---|---|---|
| 区别维度 | **功能与用户体系** | **同一功能下的数据归属** |
| 例子 | 管理后台 / 用户后台 / 代理商后台 | 同一个后台里，A 公司只看 A 的数据 |
| 菜单 | 各后台不同 | 各租户相同 |
| 登录 | 各后台独立 | 同一后台，登录后按 tenant 过滤 |
| 现有支持 | `applications` 配置（半成品，见下） | `ScopeHooks`（**已实现且两端都有**） |

**我的判断：你要的是多应用。** 但如果代理商后台里，每个代理商还要只能看自己的数据 —— 那是「多应用 + 多租户叠加」，两者都要。

这一点请你确认。下面的方案按**多应用**写，但会留出与 `ScopeHooks` 叠加的口子。

## 二、现状盘点（我读代码确认的，不是猜的）

### ✅ 已经有的（Laravel 侧，但**默认关闭**）

`packages/laravel/config/aimanong.php`：

```php
'applications' => [],   // 留空 = 单后台
```

配置结构已经定义好了：

```php
'applications' => [
    'admin' => [
        'title' => '运营后台',
        'route' => ['prefix' => 'admin'],
        'auth'  => ['guard' => 'admin', 'model' => App\Models\Administrator::class],
    ],
    'merchant' => [
        'title' => '商家后台',
        'route' => ['prefix' => 'merchant'],
        'auth'  => ['guard' => 'merchant', 'model' => App\Models\Merchant::class],
    ],
],
```

已实现的机制：

| 能力 | 状态 | 位置 |
|---|---|---|
| 应用注册表（增删改查、切换） | ✅ | `ApplicationManager` |
| **按请求路径推断当前应用** | ✅ | `ApplicationContext::doResolve()` |
| 每个应用独立的路由前缀 | ✅ | `route.prefix` |
| 每个应用独立的 auth guard | ✅ | `auth.guard` |
| 每个应用独立的用户模型 | ✅ | `auth.model` |
| 每个应用独立的域名（可选） | ✅ | `route.domain` |
| 长前缀优先匹配（`admin` 不会误匹配 `admin-x`） | ✅ | `usort` by strlen |
| **不信任 config、只信任请求路径**（踩过 4 次坑后的设计） | ✅ | `ApplicationContext` 顶部注释 |

### ❌ 缺的（这些是「多应用能用」的真正缺口）

| # | 缺口 | 后果 |
|---|---|---|
| 1 | **菜单没有应用维度** | `MenuItem` 只有 `uri/label/group/icon/sort/visible`。所有 Resource 的菜单进同一个池子 → **用户后台会看到「管理员账号」「操作日志」** |
| 2 | **权限节点没有应用维度** | `PermissionGate::slug()` = `{uri}.{action}`，没有应用前缀 → `/admin` 和 `/agent` 的 `orders.index` 是**同一个节点**。给代理商开了权限，等于也开了总后台的 |
| 3 | **Resource 注册没有应用维度** | `Registry::register(class)` 只有一个参数，声明时无法指定「这个 Resource 属于哪个后台」 |
| 4 | **ThinkPHP 侧完全没有** | `ThinkRuntime` 返回 `NullApplication`，只有单应用 |
| 5 | 应用级配置只覆盖 `route`/`auth` 两项 | 想让某个后台关掉「操作日志」等，目前做不到 |

**一句话**：多应用现在做到了「能登录、能路由」，但**没做到「菜单与权限隔离」** —— 而后者才是多应用的实质。

## 三、目标形态

### 3.1 配置

```php
// config/aimanong.php
'applications' => [
    'admin' => [
        'title' => '总管理后台',
        'route' => ['prefix' => 'admin'],
        'auth'  => ['guard' => 'admin', 'model' => App\Models\Administrator::class],
    ],
    'user' => [
        'title' => '用户后台',
        'route' => ['prefix' => 'user'],
        'auth'  => ['guard' => 'user', 'model' => App\Models\User::class],
    ],
    'agent' => [
        'title' => '代理商后台',
        'route' => ['prefix' => 'agent'],
        'auth'  => ['guard' => 'agent', 'model' => App\Models\Agent::class],
    ],
],
```

### 3.2 声明侧：Resource 归属哪个后台

**方案 A（推荐）：`applications()` 声明**

```php
class OrderResource extends Resource
{
    public static function uri(): string { return 'orders'; }

    // 属于哪些后台。不写 = 所有后台都能看到
    public static function applications(): array
    {
        return ['admin', 'agent'];
    }

    public static function menu(): array
    {
        return ['group' => '交易', 'icon' => '📦', 'sort' => 10];
    }
}
```

**方案 B：注册时指定**

```php
Aimanong::registry()->register(OrderResource::class, ['admin', 'agent']);
```

**我推荐 A**，理由：
- 声明自包含 —— AI 读一个 Resource 就知道它属于哪些后台，不用去 ServiceProvider 里找
- 符合项目「声明唯一、AI 可自省」的宪法
- `menu()` 已经在 Resource 里了，`applications()` 放一起风格一致

### 3.3 权限节点：加应用维度

```
现在：orders.index
改成：admin.orders.index / agent.orders.index
```

**但这里有个取舍**（下面第五节细说）：改 slug 会**破坏已授权的数据**。

折中方案：**保留 `orders.index` 作为默认（单应用/默认应用），只在多应用开启时加前缀**。这样单应用用户完全不受影响。

### 3.4 ThinkPHP

目标：`aimanong/thinkphp` 也能配多应用。

**关键决策**：把「应用上下文」的**解析逻辑**下沉到 `core`，Laravel 与 ThinkPHP 各实现「怎么拿当前请求路径」。

理由：现在 `ApplicationContext` 在 laravel 包里且绑 `Illuminate\Http\Request`。如果这次只在 Laravel 侧补，ThinkPHP 又要重写一遍 —— 这正是前面「同一套声明」反复出问题的根源。

## 四、要改什么（分层）

### 第一层：core（框架无关）

| 改动 | 说明 |
|---|---|
| 新增 `Contracts\ApplicationResolver` | 契约：给我当前请求路径，我告诉你属于哪个应用 |
| `MenuItem` 增加 `applications` 字段 | 菜单归属 |
| `Registry::register()` 增加可选 `applications` 参数 | 注册时归属 |
| `MenuRegistry::visible()` 增加按当前应用过滤 | **核心** |

`ApplicationResolver` 契约草案：

```php
interface ApplicationResolver
{
    /** 当前应用名（单应用时返回默认名） */
    public function current(): string;

    /** 是否启用了多应用 */
    public function enabled(): bool;

    /** 所有已注册应用名 */
    public function names(): array;

    /** 某应用的路由前缀 */
    public function prefix(string $name): string;

    /** 某应用的守卫名 */
    public function guard(string $name): string;

    /** 某应用的用户模型类 */
    public function model(string $name): string;
}
```

### 第二层：laravel

| 改动 | 说明 |
|---|---|
| `ApplicationManager` 实现 `Contracts\ApplicationResolver` | 复用现有逻辑 |
| `PermissionGate::slug()` 支持应用前缀 | 多应用开启时加前缀 |
| `ResourceController` 按当前应用过滤 Resource | 防止跨应用访问 |
| 应用级配置覆盖扩展到更多键 | 如 `foundation.*` |

### 第三层：thinkphp

| 改动 | 说明 |
|---|---|
| 新增 `ThinkApplication` 实现 `Contracts\ApplicationResolver` | 按 TP 的 pathinfo 推断 |
| `ThinkRuntime::context()` 返回真实应用上下文 | 替换 `NullContext` |
| 路由按应用分组注册 | `/user/...` `/agent/...` |
| 每个应用独立的 guard | 替换单一 `ThinkGuard` |

### 第四层：验证

| 改动 | 说明 |
|---|---|
| e2e：多应用场景 | 三个后台各自登录、菜单不串、权限不串 |
| 反例：跨应用访问应 403/404 | 不是静默成功 |
| 单应用回归 | 保证 `applications => []` 行为完全不变 |

## 五、关键决策点（需要你拍板）

### 决策 1：权限 slug 要不要加应用前缀？

| | 加前缀 | 不加前缀（靠应用隔离上下文） |
|---|---|---|
| 隔离强度 | 强：节点本身就是不同的 | 弱：靠运行时上下文判断 |
| 兼容性 | **破坏已有授权数据**（要迁移） | 无影响 |
| 复杂度 | 低 | 高（每个判定都要带上下文） |
| 自省清晰度 | AI 看 slug 就知道是哪个后台 | 看不出来 |

**我的建议：加前缀，但只在多应用开启时。** 单应用（`applications => []`）保持 `orders.index` 不变，这样现有项目零影响。

### 决策 2：用户表是一张还是多张？

| | 一张表 + type 字段 | 每个应用一张表 |
|---|---|---|
| 例子 | `users` 表加 `type`（admin/user/agent） | `admin_users` / `users` / `agents` |
| 现状 | 现在是每张一张（`auth.model` 各指定） | ✅ 已支持 |

**现状已经支持「每个应用一张表」**（配置里 `auth.model` 就是各应用独立的）。我建议**保持现状**，不引入 type 字段 —— 因为代理商和普通用户的字段差别通常很大。

### 决策 3：菜单是按应用隔离，还是按权限隔离就够？

现状 `visible()` 只按权限过滤。**如果权限节点加了应用前缀，菜单隔离就自动成立了**（因为不同应用的 slug 不同，权限判定自然分开）。

所以：**决策 1 定了，决策 3 自动解决**。这也是我推荐"加前缀"的原因 —— 一处改动解决两件事。

### 决策 4：ThinkPHP 这次一起做吗？

| | 一起做 | 先只做 Laravel |
|---|---|---|
| 工作量 | 大（约 2 倍） | 小 |
| 一致性 | 好 | 又要补一次（前面踩过 14 处差异的教训） |
| 风险 | 高 | 低 |

**我的建议：这次把 core 层抽象做扎实（第一层），Laravel 侧落地（第二层），ThinkPHP 侧这次只做「单应用仍可用」的兼容，明确标注多应用未实现。** 等 Laravel 侧跑稳了再补 TP —— 这比两边同时开工更稳，因为多应用的语义（尤其是权限前缀）需要先在一个框架上定型。

## 六、风险与取舍

| 风险 | 说明 | 缓解 |
|---|---|---|
| **权限前缀破坏已有授权** | 已有项目升级后权限失效 | 只在多应用开启时加前缀；提供迁移命令 |
| **应用上下文推断错误** | 长前缀已处理；但域名模式未验 | 补 e2e：路径模式 + 域名模式 |
| **菜单串台** | 用户后台看到管理菜单 | 权限前缀解决 + 补断言 |
| **跨应用访问 Resource** | 在 agent 后台访问只在 admin 注册的 Resource | 控制器层过滤，返回 404 而非 403（防探测） |
| **ThinkPHP 侧二次返工** | 先在 Laravel 定型 | 抽象放 core |

#### 过程中测试抓到的一个真 bug

第一版在单应用下也做归属过滤 →
声明了 `applications(['admin','agent'])` 的 Resource **凭空消失**。
单应用项目里根本没有 admin/agent 之分。

修法：**只在 `enabled() === true` 时过滤**。
这正是「单应用零影响」这条验收标准的价值 —— 它立刻红了。

#### 另一个踩到的坑

我的测试 `tearDown` 只 `Drivers::reset()`，
把 bootstrap 注册的那套驱动清掉了 → 后面的
`SchemaIntrospectorTest` 拿到 `NullIntrospector` 而红，
**红的位置离原因很远**。已改为完整恢复驱动集。

| **第 2 段** | laravel：权限 slug 加前缀（仅多应用时）+ 控制器按应用过滤 | 三后台各自登录、权限不串、跨应用访问 404 |
| **第 3 段** | 配置与 install：应用级配置覆盖扩展 + `applications` 引导 | 新项目能一次配出三个后台 |
| **第 4 段** | thinkphp：应用解析 + 路由分组 + 各应用 guard | TP 侧多应用 e2e |

每段我都会：先做 → 跑全部门禁 → 用真实例子（三个后台）验证 → 再进下一段。

## 八、一句话总结

**多应用的「骨架」（路由/守卫/前缀/模型）已经在了，缺的是「血肉」（菜单隔离、权限隔离、Resource 归属）。**

按这个方案，改动集中在 **core 的一处抽象 + Laravel 的权限前缀**，就能让 `/admin` `/user` `/agent` 三个后台真正隔离。

## 需要你确认的 3 件事

1. **我理解的「多应用」对不对？**（不是多租户数据隔离）
2. **权限 slug 加应用前缀**，你能接受「多应用开启时节点改名」吗？（单应用不受影响）
3. **这次先做 Laravel、ThinkPHP 后续补**，可以吗？
