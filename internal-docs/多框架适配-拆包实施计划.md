# 拆包实施计划（aimanong/core · laravel · thinkphp）

> 依据：[多框架适配-PoC报告.md](./多框架适配-PoC报告.md)
> 目标架构（PoC 实测后确定，非推测）：

```
aimanong/core       框架无关内核 —— 0 个 illuminate 依赖
aimanong/laravel    Laravel 12 驱动
aimanong/thinkphp   ThinkPHP 8.1 驱动 —— 永远不接触 illuminate/*
aimanong/framework  元包（require core + laravel），老用户命令不变
```

**为什么要拆包而不是抽接口**：PoC 实测证明 `composer require aimanong/framework`
装进 ThinkPHP 项目会让对方的应用**启动即致命错误**，而 Composer 报零冲突。
障碍在依赖层，不在接口层。只要 `framework` 的 `require` 里有 `illuminate/*`，
它就能落进任何非 Laravel 项目。详见 PoC 报告第一节。

## 一、分段计划

每段都**独立可发布**、**独立可验证**，跑完不留半成品。

### 第 1 段：Schema 层抽掉最后 3 处 Illuminate ✅ 已完成（2026-10-13）

**为什么先做这个**：`Schema/Compiler.php` 是四份产物的枢纽，
也是宪法第三条「零隐式」的主要执行者（幽灵列检测）。
它现在把 `Schema::` 门面、`Eloquent\Relation`、`Eloquent\Model` 写死了三处，
导致**换框架后幽灵列检测会静默失效** —— 这是最不能接受的降级。

**做法**：引入 `Contracts\SchemaIntrospector`，把「查表结构 / 判关联 / 判访问器」
三件事交给驱动实现。

**验证**：现有 184 个测试全绿 + e2e 102/102，行为零变化。

**实际结果**（已完成）：
- 新增 `Contracts\SchemaIntrospector` + `Schema/Introspector/`（Eloquent / Null / Resolver）
- `Schema/Compiler.php` 现在**零 Illuminate**；3 处依赖全部收进 `EloquentIntrospector`
- 测试 **184 → 200**（+16），断言 655 → 683
- e2e 102/102、http-e2e 32/32、`tsc --strict` 全绿
- **顺带补上一个真实覆盖缺口**：原先所有单测都因「无 DB → 跳过检测」而早退，
  幽灵列检测的数据库路径**从未被跑过** —— 184 个测试全绿也证明不了它是对的。
  现在有 `EloquentIntrospectorTest`（真 sqlite）与 `SchemaIntrospectorTest`
  （契约层，不连库）两块覆盖。
- 真机验证：在 demo-app（真 Laravel + sqlite）里故意把 `name` 写成 `nmae`，
  `ai:verify` 正确报 `column:nmae` 并给出 `did_you_mean: name`。
  证据：`poc-evidence/10-schema-introspector-e2e-proof.txt`

### 第 2 段：建 `packages/core`，搬入 0 依赖层 ✅ 已完成（2026-10-13）

**先做了一件计划里没写、但不做就搬不动的事：抽驱动接缝。**

审计发现「0 依赖」其实不成立 —— 待搬目录里有 4 处直连到要留下的驱动：

| 位置 | 依赖 | 处理 |
|---|---|---|
| `Form/Concerns/ResolvesDictionary`、`Grid/Column` | `Foundation\Dict\Dictionary` | → `Contracts\DictionarySource` |
| `Menu/MenuRegistry` | `Auth\PermissionGate`（静态 API） | → `Contracts\PermissionChecker` + 实例适配器 |
| `Schema/Emitters/JsonSchemaEmitter` | `Foundation\Upload\Uploader` | → `Contracts\UploadSpec` |
| `Schema/Compiler`、`Support/ColumnResolver` | `Model`/`Relation`/`Schema` 门面 | → `Contracts\SchemaIntrospector`（第 1 段成果） |

新增 **`Aimanong\Support\Drivers`** 作为 core 与框架之间的**唯一接缝**。

> **两类缺失，处理方式故意不同**（写进类注释并有测试锁定）：
> - 字典 / 权限 / 上传 → **抛 `DriverNotRegisteredException`**。
>   用户**声明**了 `->dict()`，兑现不了就是幽灵能力（宪法第三条）。
> - Schema 内省 → **返回 null**，调用方跳过检测。这项检查本就尽力而为。
>
> 混为一谈的后果：要么无谓报错，要么静默产出错误 schema。

**搬包结果**：

| | 文件 | 行数 |
|---|---:|---:|
| `packages/core`（零 illuminate） | 70 | 5,904 |
| `packages/framework`（驱动 + Laravel 绑定） | 64 | 12,368 |

Eloquent 驱动移入独立命名空间 `Aimanong\Drivers\` —— 拆包时整个目录搬去 laravel 包。

**新增三道关卡**（都把「声明」变成「事实」）：

1. **`scripts/check-core-purity.sh`** —— core 里出现 `use Illuminate` /
   `use Laravel`，或代码行里的全限定名，直接失败。
   已用真实反例验证过它会拦。
2. **`publish-framework.sh` 依赖守卫** —— 发布 framework 前确认它依赖的
   `aimanong/*` 已在 Packagist 上。否则会发出一个「永远装不上」的包，
   而发布过程本身一切正常。
3. **e2e 退出码保证** —— 见下方「顺带修掉的三个真问题」。
   修完立刻暴露出两个**早就存在、一直被假绿盖住**的缺陷（CI 长期在说谎）。

**验证**：PHPUnit 209/209（+9）、PHPStan L8 ✅（含 core，168 文件）、
Pint ✅（含 core 70 文件）、framework-e2e 102/102、http-e2e 32/32、tsc --strict ✅。

#### 顺带修掉的三个真问题（都属「关卡在撒谎」）

**① 搬包时 e2e 崩了，但 pre-release 报「✅ 通过」。**
`framework-e2e.php` 硬编码了 `packages/framework/src/Grid/Grid.php` 等 11 处源码路径，
文件一搬就变成「不存在」。更糟的是 Laravel 的全局异常处理器会把
`ErrorException` 渲染出来却**不改变退出码**，而 `pre-release.sh` 只看退出码 ——
于是**崩了的测试被显示成通过**。

修法：① 加 `fwSrc()` 助手，同时搜 core 与 framework 两个包
② 加 `register_shutdown_function`：没跑到结尾即判定失败
③ 末尾显式 `exit($fail > 0 ? 1 : 0)`。
`http-e2e.php` 同样问题，一并修。
三个场景都实测过：中途崩溃 → exit 1；断言失败 → exit 1；正常 → exit 0。

**② 修完退出码后，CI 红了 —— 但那两个失败早就存在，只是被假绿盖住。**

| | 修复前（显示「✅ 通过」） | 修复后（真实） |
|---|---|---|
| framework-e2e | `92 / 94` | **`95 / 95`** |
| http-e2e | `9 / 24` | **`24 / 24`** |

也就是说 CI 的端到端这一关**长期在说谎**：15 个失败被当成通过。

根因一：**管理员密码从来没设对**。`setup-demo.sh` 先让 `aimanong:install`
建一个随机密码的管理员，再跑一次带 `--admin-password=admin123` 的想覆盖它 ——
而第二次的实际输出是「已存在管理员账号，跳过创建（不会重置已有密码）」。
这一步还写着 `|| true` 吞掉失败。修法：第一次安装就带上账号密码。

根因二：**region 扩展从未被注册**。region 声明的
`extra.aimanong.extension` 是**死元数据**（全仓库无代码消费，装命令也不扫），
所以全新项目装完 region 后 `RegionExtension` 根本不 boot，
`FieldType::fieldViewFor('region')` 是 null —— 省市区字段退化成普通文本框。
修法：demo 里显式登记进 `config('aimanong.extensions')`。

**③ `Dictionary::codes()` 插错位置**，把 `all()` 的 `@return` 形状注记抢走，
导致 `DocsCommand` 类型推断退化。PHPStan 抓到 —— 关卡的价值。

#### 本段发现、留给后续的问题

- **`extra.aimanong.extension` 是死元数据**。插件必须在
  `config('aimanong.extensions')` 里手工登记，否则静默不生效。
  这是宪法第三条（零隐式）的典型违规：声明了却不被消费。
  要么实现自动发现，要么删掉这段元数据并写清登记步骤。
- **`aimanong:install` 会重新发布 `config/aimanong.php`**，
  覆盖用户已有的自定义内容（本地 demo 的字典声明就是这样被清空的）。
  这是数据丢失，值得单独评估。


#### 本段遗留（明确不做）

- `aimanong/core` **尚未发布到 Packagist**。所以**现在还不能发 framework** ——
  依赖守卫会拦住。发布 core 需要新建 GitHub 仓库 `aimanong-core`，
  这一步需要用户确认。
- `Ai` / `Application` / `Extend` / `Services` / `Support(部分)` / 根目录文件
  仍在 framework，各带 2~6 处 Illuminate 依赖，留待第 3 段抽象后搬入。


- 新建 `packages/core`（composer 包名 `aimanong/core`，PSR-4 `Aimanong\`）
- 搬入：Form / Grid / Show / Tree / Ui / Menu / Exceptions / Schema / Contracts / Ai /
  Support / Services / Application / Extend + 根目录的框架无关文件
- `packages/framework` 改为 `require aimanong/core`，其余原样
- **发布流程改动**：`publish-framework.sh` 要支持多包（已有框架，加 core 即可）

**验证**：`framework` 的 184 测试 + e2e 全绿；`composer require aimanong/framework`
行为不变（Laravel 用户零感知）。

### 第 3 段：建 `packages/laravel`，`framework` 变元包 ✅ 已完成（2026-10-13）

**实际结构**：

| 包 | 版本 | 内容 |
|---|---|---|
| `aimanong/framework` | 1.9.0 | **元包**（type: metapackage）—— 用户装的、对外的产品版本 |
| `aimanong/laravel` | 1.0.0 | Laravel 12 驱动 + 包资源（views / config / routes / database） |
| `aimanong/core` | 1.0.0 | 框架无关内核，零 illuminate |

`packages/framework` 现在只有一个 composer.json。

#### 拆包逼出来的一个真问题：版本号指谁

一次安装引入三个包、三个版本号。`Aimanong::version()` 原先读「自己所在包」的
composer.json，拆完就变成 laravel 的 1.0.0 —— 而后台界面顶上显示的就是它。

**定论：对外版本号 = framework 元包的版本。** 内部包升版不影响用户看到的数字。

实现踩了一个坑：`framework` 是 metapackage，**Composer 不为它建目录** ——
`vendor/aimanong/framework/composer.json` 根本不存在。只按文件路径找会
**静默回退成 laravel 的 1.0.0**。所以：仓库内开发走路径；装进应用走
Composer 的 `InstalledVersions`（metapackage 也记录在案）。
两种布局都实测返回 1.9.0。

#### 顺带修的

- e2e 里 `$fw` 还指着 packages/framework（那里已只剩 composer.json），
  「模板存在性守卫」直接读不到模板。现在 `$fw` 指驱动包，
  路径助手提到文件开头（原先有一处硬编码在它定义之前，搬一次崩一次）。
- **发行同步检查收紧**：原先直接比 `composer.json` 与 Packagist 最新版，
  于是「开发中版本领先」被误报成「发版遗漏」（拆包期间就踩到：
  framework 1.9.0 依赖的 laravel 还没发，framework 自然发不出去，CI 却红）。
  改成三条同时满足才硬校验：① 有 tag `v<version>` ② 该 tag 上有本包的
  composer.json ③ 其 version 与 tag 名一致。
  已用真实反例验证：造出「framework 9.9.9 打了 tag 未发布」→ 精确拦下；
  其他包的 `v1.0.0` 正确跳过。

**验证**：

| 项 | 结果 |
|---|---|
| PHPUnit | 209 tests / 708 assertions ✅ |
| PHPStan L8（含 core） | ✅ 168 文件 |
| Pint（含 core） | ✅ 176 文件 |
| core 纯度门禁 | ✅ 70 文件 / 5904 行零依赖 |
| framework-e2e | ✅ 95/95（CI）／101/101（本地含自定义资源） |
| http-e2e | ✅ 24/24（CI）／31/31（本地） |
| `tsc --strict` | ✅ 1794 行（CI） |
| 真实安装 | demo lock：core 1.0.0 + laravel 1.0.0 + framework 1.9.0(metapackage) + region 1.0.0，界面版本 1.9.0 |

#### 发布与最终验收 ✅

| 包 | Packagist | 仓库 |
|---|---|---|
| `aimanong/core` | 1.0.0 | aimanong-core |
| `aimanong/laravel` | 1.0.1 | aimanong-laravel |
| `aimanong/framework` | 1.9.1 | aimanong-framework |
| `aimanong/region` | 1.0.0 | aimanong-region |

**最终验收**：一个 composer.json 里**没有任何本地 path 仓库**的项目，
从 Packagist 装 → core 1.0.0 + laravel 1.0.1 + framework 1.9.1(metapackage)
+ region 1.0.0 → 后台完整可用（http-e2e **24 / 24**）。
证据：`poc-evidence/13-final-acceptance-packagist.txt`

#### 1.9.1：只有真装一次才看得见的 bug

1.9.0 发布后做上面的验收时发现，界面显示的版本号是 **1.0.0**（laravel 的）
而不是产品版本 1.9.0。

根因：`framework` 是 metapackage，Composer 不为它建目录，
`Aimanong::version()` 的路径候选落空 → 落到「本包 composer.json」→ 1.0.0。

修法：把「用 Composer 的 `InstalledVersions` 取产品包版本」提到最前，
且**只认 `aimanong/framework`**：
Composer 会把 **root 包**一并放进 InstalledVersions，而驱动包在仓库里
跑测试时它自己就是 root —— 把 laravel 也列进候选，测试环境反而会错。

单测抓不到这个（测试环境的 root 包情况与真实安装不同），
只有「从 Packagist 真装一次并打开界面」才会暴露。
这是 AGENTS.md 第 9 条「验收标准盯着用户可感知的结果」的一个实例。

#### 顺带修：包 tag 由各包版本派生

发布脚本原先把**主仓库 tag 名**原样推到包仓库。主仓库 tag 是产品级的
（`v1.9.0`），而各包有自己的版本线 —— 原样推会在 laravel 仓库上造出
一个根本不存在的 `v1.9.0`。（第一次发 laravel 时 `v1.9.0` 还没打，
侥幸跳过。）现在远端 tag 一律用「该提交上本包 composer.json 的 version」。

## 二、风险与对策

| 风险 | 严重度 | 对策 |
|---|---|---|
| 搬包过程漏改引用导致大面积报错 | 高 | 一段一提交，每段跑全量测试；PHPStan L8 会抓出类型级断裂 |
| `framework` 从实体包变元包，老用户锁版本受影响 | 中 | 元包版本号与 core/laravel 解耦；发 2.0.0 明确标注 |
| core 里藏着运行期才暴露的 Illuminate 依赖（`class_exists` 判断、字符串类名） | 高 | 用 PHPStan 的 `bannedCode` 或 CI 加一条「core 目录 grep 不到 Illuminate」的硬门禁 |
| Packagist 多包发布遗漏 | 中 | `pre-release.sh` 的版本同步检查扩到 4 个包（现在是 2 个） |
| 模板的 3 条硬规则要改动现有模板写法 | 中 | 已在 PoC 报告里写明；落地时加静态检查 |

### 重点：给 core 加一条硬门禁

拆包最容易失败的方式不是搬错文件，而是**搬完之后 core 里又悄悄长回 Illuminate 依赖**
（AI 生成代码时尤其容易）。所以要加：

```bash
# CI: core 包内不得出现 Illuminate/Laravel
! grep -rq "use Illuminate\|use Laravel" packages/core/src/
```

这条门禁比任何文档都有效 —— 它把「core 是框架无关的」从**声明**变成**运行时事实**
（宪法第三条）。

## 四、与宪法的一致性

| 条款 | 本计划如何满足 |
|---|---|
| ① AI 优先 | 多一个框架 = 多一批可用项目；DSL 层不变，AI 写的声明两边通用 |
| ② 声明唯一 | core 是唯一真源；laravel/thinkphp 只是驱动，不重复声明 |
| ③ 零隐式 | core 的依赖门禁 + `SchemaIntrospector` 让幽灵列检测在两边都真生效 |
| ④ 可自省 | 能力面从 core 产出，与驱动无关 |
| ⑤ 可验证 | 每段都有可跑的验收；第 3 段的验收点直接是「TP 能启动」 |
| ⑥ 错误可自愈 | 驱动缺失时报明确错误，不静默降级 |
| ⑦ 人不做技术决定 | 驱动由配置选择，不需要人改声明代码 |
