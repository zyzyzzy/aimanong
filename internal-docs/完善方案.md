# 项目完善方案

> 2026-10-11 · 基于对 v1.7.1 的实际排查（不是凭印象）
>
> 排查方法：读代码 + 真实环境实测。所有结论都给出可复现的证据。

---

## 一、结论先行

项目**功能面已经相当完整**（8 个版本、123 个 PHP 类、30 个测试文件、13 页文档），
但我这次系统排查发现 **8 个问题**，其中 **3 个是「不修就会出事」的级别**：

| 级别 | 问题 | 后果 |
|---|---|---|
| 🔴 **P0** | **CI 的端到端 job 一直在失败** | 我加的 job 从未在 CI 上验证过 —— 等于没有质量门禁 |
| 🔴 **P0** | **`config:cache` 后整个后台 500** | 任何人按 Laravel 惯例部署生产，都会撞上 |
| 🔴 **P0** | **登录无速率限制** | 暴露公网的后台可被无限次爆破密码 |

**最该说的是第一条**：我这几轮一直在本地跑门禁并报告「全绿」，
但**从来没看过 CI 的实际结果**。刚查了才发现 e2e job 从加进去那天就是失败的。

## 二、逐项分析

### 🔴 P0-1：CI 端到端 job 一直失败（最紧急，也最该检讨）

**证据**：

```
$ gh run list --limit 5
completed  failure  CI  main  push  38203769050  48s   ← 失败
completed  success  Mirror to Gitee  main  push  ...  7s
```

```
JOBS
✓ PHP 8.2 兼容性            in 20s
✓ 框架质量门禁（PHP 8.3）    in 26s
X 端到端（真实 HTTP）        in 26s     ← 我加的 job
✓ 发布前检查                in 43s
```

**失败原因**：

```
- Root composer.json requires aimanong/framework @dev
- aimanong/framework 1.7.1 requires laravel/mcp ^0.4
- laravel/mcp v0.4.2 requires illuminate/container ^10.49.0|^11.45.3|^12.41.1
- ...but these were not loaded, likely because it conflicts with another require.
```

`setup-demo.sh` 用 `composer create-project laravel/laravel` 建项目时，
拿到的是**最新的 Laravel 骨架**，其 illuminate 版本与 `laravel/mcp`
要求的版本区间对不上。

**为什么这最该检讨**：

> 我在引入这个 job 时**没有验证它在 CI 上能否跑通** ——
> 本地跑 `setup-demo.sh` 是成功的（本地已有 composer 缓存与更早的骨架版本）。
>
> 结果是我交付了一个「看起来加了质量门禁」但实际上一直红着的 job。
> 这比不加更糟：绿着的门禁会让人放心，红着的会被人忽略。

**修复思路**：

```bash
# 建项目时锁定 Laravel 版本区间，与 framework 的 require 对齐
composer create-project "laravel/laravel:^12.0" "$DEMO" --no-interaction
```
并在 CI 里**显式断言 job 必须绿**（现在已经是失败状态，修好后自然变绿）。

**工作量**：~1 小时（含在 CI 上验证）

### 🔴 P0-2：`config:cache` 后整个后台 500

**证据（实测）**：

```
$ php artisan config:cache
   INFO  Configuration cached successfully.

$ curl /admin/admin-users
   HTTP 500

$ tail storage/logs/laravel.log
   local.ERROR: Auth driver [admin] for guard [admin] is not defined.
```

**根因**：

框架在 `AimanongServiceProvider::register()` 里**动态改写 config** 并用
`Auth::extend()` 注册自定义 guard：

```php
// src/AimanongServiceProvider.php:294, 448
config(['auth' => $auth]);

Auth::extend($guard, function (...) { ... });   // 运行时注册 driver
```

而 `config:cache` 会把 config **序列化冻结**。之后 `Auth::extend()` 注册的
driver 在解析 guard 时不可见 → `Auth driver [admin] is not defined`。

**为什么严重**：

Laravel 官方部署文档的第一步就是：

```bash
php artisan config:cache
php artisan route:cache
php artisan view:cache
```

**任何按惯例部署的用户都会撞上，而且报错信息（「driver 未定义」）
完全指不到真正的原因（config 被缓存了）。**

**文档现状**：全仓库 grep `config:cache` → **零命中**。没有任何警告。

**修复思路**（两选一，我建议 A）：

| 方案 | 做法 | 评价 |
|---|---|---|
| **A. 让框架兼容 config:cache** | guard 注册移到 `boot()`，或改用 `Auth::viaRequest()` 这类不依赖 config 缓存的形式 | 根治，但需验证多应用场景 |
| B. 明确不支持并警告 | 文档写清「不要跑 config:cache」，`aimanong:install` 检测到时给出提示 | 权宜，但用户会困惑 |

**工作量**：A 约 3-4 小时（含多应用回归）；B 约 30 分钟

### 🔴 P0-3：登录无速率限制

**证据（实测）**：连续 10 次错误密码

```
第 1 次错误密码 → 422
第 2 次错误密码 → 422
...
第 10 次错误密码 → 422      ← 完全没有拦截
```

**根因**：

```php
// routes/admin.php:27-28
Route::post('auth/login', [AuthController::class, 'login'])->name('login.post');
// 没有 ->middleware('throttle:...')
```

全仓库 grep `throttle` → **0 处**。

登录日志**记录了**失败（这是好的），但**日志不能阻止攻击**。

**威胁模型**：

- 攻击者拿到后台地址 + 常见账号名，即可无限次尝试密码
- 没有速率限制、没有失败锁定、没有验证码
- 一个暴露公网的后台，弱密码账号会在可接受时间内被攻破

> 这是**安全基线**问题。竞品（若依 / yudao）都有登录失败锁定。

**修复思路**：

```php
Route::post('auth/login', ...)
    ->middleware('throttle:5,1');   // 每分钟 5 次
```

更完整一点：

| 措施 | 说明 |
|---|---|
| IP + 账号双维度限流 | 防单 IP 爆破，也防分布式打同一账号 |
| 失败 N 次后锁定 X 分钟 | 可选，配置化 |
| 登录日志增加「当前 IP 的连续失败次数」 | 让管理员能看出正在被爆破 |
| 配置开关 | `aimanong.auth.throttle` |

**工作量**：~2 小时（含测试与文档）

### 🟡 P1-1：三个「幽灵能力」

本项目最反对的就是「声明了却不能用」，但代码里还留着三个：

| 能力 | 声明处 | 后端 | 前端 | 性质 |
|---|---|---|---|---|
| `tree()->draggable()` | `Tree.php:59` | ✅ `/move` 接口 | ❌ 无拖拽 UI | **已标注** `draggable_supported: false` |
| `column()->filter()` | `Column.php:63` | ✅ `?filters[x]=y` 生效 | ❌ 无筛选控件 | 只有 schema 标志 |
| `grid()->batchActions()` | `Grid.php:75` | ❌ 后端也没实现 | ❌ 无 UI | **纯幽灵** |

**前两个至少「后端能用」**，第三个（`batchActions`）是**完全没实现**。

**第六轮 AI 实测的真实反馈**：

> `->filter()` 是个空壳 —— schema 里老实产出 `"filterable": true`，
> API 层 `?filters[status]=pending` 也真生效，但页面上一个筛选控件都不渲染。
> 我最后移除了这个声明 —— 留着只会骗下一个读 schema 的人。

**修复思路**（按性价比排序）：

| 选项 | 工作量 | 效果 |
|---|---|---|
| **A. 补齐筛选 UI** | 半天 | 消除幽灵能力，且这是竞品标配 |
| **B. 补齐批量操作 UI** | 1 天 | 列表页批量删除/导出 |
| **C. 补齐树形拖拽** | 1 天 | 树形资源可拖拽排序 |
| D. 全部标注为「未实现」 | 1 小时 | 诚实但不解决问题 |

**建议先做 A**（筛选），因为它是**最常被用到**的，且已有 AI 实测反馈佐证。

### 🟡 P1-3：前端单文件 927 行

```
resource.blade.php   927 行
  ├─ HTML 模板  288 行
  └─ JS 逻辑    640 行
```

**这是否算问题？我的判断是：现在还不是。**

理由：

1. **零构建是明确的产品约束**（`UI重做需求.md` 硬约束），拆分意味着引入构建步骤
2. 927 行对一个 SPA 页面不算离谱（很多 React 页面单文件更长）
3. 拆分收益（可读性）与成本（构建链 + 双份产物漂移风险）不成正比

**但要设一个阈值**：如果超过 **1200 行**，或第 4 个页面需要复用同一套逻辑，
就应该认真考虑拆成多个 `partials/` 片段（用 `@include`，仍然零构建）。

> 现在其实已经这么做了：`partials/upload.blade.php`（249 行）
> 就是抽出来的，被 resource 和 profile 两处复用。

### 🟡 P1-4：测试只有 Unit，没有 Feature 测试

```
tests/Unit/     30 个文件    ✅
tests/Feature/   0 个文件    ❌
```

**影响**：HTTP 层的行为（中间件、认证、CSRF、权限拦截）**没有 PHPUnit 覆盖**，
只能靠 `tests/e2e/http-e2e.php`（32 项）。

好在 e2e 补上了这块，所以**这不是紧急问题**。但 e2e 需要真实服务，
没法在每次 `composer test` 时跑。

**建议**：加一层 `tests/Feature/`（用 Laravel 的 `RefreshDatabase` + 内存 SQLite），
覆盖最关键的几条：登录、权限拦截、只读资源 403、上传校验。

**工作量**：~半天（需先搭 Feature 测试基础设施）

## 四、我的检讨

这次排查暴露了一个**方法论问题**，值得单独说：

> **我把「本地门禁全绿」当成了「质量合格」，但从来没有验证过
> 交付出去的东西（CI job）在目标环境里是否真的工作。**

具体表现：

1. 加了 e2e job，**没跑过 CI 就宣布完成**
2. 写了 `config:cache` 会导致 500，**因为本地从不跑它，所以没发现**
3. 登录无限流，**因为我从没想过要测这个**

前几轮我反复强调「验证要看用户可感知的结果」，但**我自己在「CI 是否真的绿」
这件事上，用的恰恰是「看起来加了」的标准**。

**建议加入自检清单**：

| # | 新检查项 |
|---|---|
| 10 | **改了 CI 配置 → 必须 `gh run list` 确认真的绿了** |
| 11 | **改了框架启动流程 → 必须测 `config:cache` + `route:cache` 后的行为** |
| 12 | **涉及认证/上传/权限 → 必须想一遍「攻击者会怎么打」** |

---

## 五、一句话总结

> 项目**功能面已经完整**，但有 **3 个 P0 问题**挡在「可以让人用」前面：
> CI 门禁是红的、生产部署会 500、登录能被无限爆破。
>
> 这三个都不是「功能没做完」，而是**「交付前没在真实环境里验证」**——
> 与我前几轮反复强调的原则，恰恰是同一个错误的两种表现形式。
