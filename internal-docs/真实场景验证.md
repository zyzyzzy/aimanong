# 真实业务场景验证记录

> v1.0 之后的验证：用**真实电商需求**压力测试，找 AI 测试集覆盖不到的盲区。

## 设计

不同于前五轮 AI 实测（任务描述直接给验收标准），本次模拟**真实客户需求文档**：

- 三张表：分类（树形）、商品（16 列，含软删除/JSON/状态机）、订单（13 列，含外键）
- 需求用**业务语言**描述，包含**框架可能做不到的需求**（刻意压力测试）
- 需求文档里混入了典型的"客户想要但不现实"的诉求

## 刻意设置的压力点

| 需求 | 预期挑战 |
|---|---|
| "库存少于 10 的要能一眼看出来" | 条件样式 —— 框架当时**不支持** |
| "列表里要能看到分类，新增时能选分类" | 关联列 —— 框架当时**不支持** |
| "状态要显示得直观一点，别显示英文" | 映射能力（框架支持） |
| "商品字段多，建议分步骤填写" | 分步表单（框架支持） |
| "要能导出 Excel 给运营" | 导出（框架支持 CSV，非 xlsx） |
| 软删除表 | 框架是否自动排除已删除记录 |

## 结果：17/19

**框架支持良好（17 项）**：树形、搜索、排序、金额格式、状态映射、布尔展示、
导出、分步表单、必填校验、订单状态映射

**框架暴露短板（2 项）**：

| # | 需求 | AI 的绕法 | 问题 |
|---|---|---|---|
| 1 | 库存<10 标红 | 无法实现，用 `badge()` 代替 | 框架**无任何条件样式能力** |
| 2 | 列表显示分类名 | `->map(self::categoryOptions())` —— 自己查表拼映射 | 框架**无关联列**，AI 被迫手写映射 |

## 这两个短板说明了什么

**它们在前五轮 AI 实测中完全没暴露** —— 因为那些任务都是单表、无关联、无业务规则。

**真实场景与示例场景的差距**：

| | 示例场景 | 真实场景 |
|---|---|---|
| 数据关系 | 单表 | 多表外键 |
| 业务规则 | 无 | 状态机、阈值告警 |
| 字段数量 | 5-10 | 13-16 |
| 展示要求 | "显示这个字段" | "要能一眼看出来" |

**结论**：只跑"生成 CRUD"这类任务，永远发现不了这类短板。

## 修复记录（第一件：真实场景验证）

### 修复 1：关联列（框架原来不支持）

**问题**：商品列表要显示"分类名"，框架只能显示 `category_id`。
AI 被迫手写 `->map(self::categoryOptions())` —— 自己查表拼映射。

**修复**：
- `Column::relation('category.name')` 显式声明
- 点号命名自动识别：`$grid->column('category.name', '分类')`
- Repository **自动 `with()` 预加载**，避免 N+1
- 前端 `cellValue()` 深取关联值

### 修复 2：条件高亮（框架原来完全没有）

**问题**：需求"库存少于 10 要标红"在框架里**无法实现**。

**修复**：
- `dangerWhen(运算符, 阈值, 级别)` —— 通用形式
- `dangerBelow(10)` / `warningAbove(100)` —— 语义化快捷方法
- **条件用「运算符 + 阈值」而非闭包** —— 保证可序列化、AI 可读
- 前端 `cellClass()` 按规则判定，支持 danger/warning/success 三级

### 修复 3：幽灵列检测误拦关联列

**问题**：加了关联列后，`category.name` 被幽灵列检测拦截
（它按整串比对表列，而 `name` 属于关联目标表）。

**修复**：检测器识别点号路径 —— 只要点号前的关联在模型上存在即放行。

## 第三件：首个官方插件（验证插件机制）

**插件**：`aimanong/region` —— 中国省市区三级联动选择器

选它作为首个官方插件的理由：
- 国内后台**最刚需**的扩展（几乎每个业务都要）
- 框架核心**不应该**内置（数据量大、非通用）
- 能同时验证插件机制的多个维度

### 用真实插件验证，暴露了 2 个机制缺口

**缺口 1：字段类型硬编码，插件无法注入**

原来 `FieldType::TYPES` 是 `const`，插件无法注册新字段类型。

修复：
- `FieldType::register(name, jsonType, phpType, fieldClass)` —— 运行期注册
- `FieldType::all()` 返回内置 + 插件注册
- `Extension::field($class)` —— 插件声明字段类型的入口

**缺口 2：Form 没有字段方法入口**

即使注册了类型，`$form->region()` 仍然不存在 —— `Form` 只有硬编码的 30 个方法。

修复：`Form::__call()` —— 但**不是任意魔法入口**：

```php
public function __call(string $method, array $arguments): Field
{
    $class = FieldType::fieldClass($method);

    if ($class === null) {
        // 未注册 → 抛异常 + 列出可用类型（AI 可自愈）
        throw new \BadMethodCallException(
            "Form 上不存在方法 {$method}()。\n可用字段类型: {$available}\n"
            ."提示：插件提供的字段需先在扩展中注册（Extension::field()）。"
        );
    }

    return $this->add(new $class(...$arguments));
}
```

**关键设计**：只服务**已注册**的类型，未注册一律报错并给出可用列表。
这与框架铁律「零隐式魔法」一致 —— 保留可预测性，同时留出扩展点。

### 端到端验证（浏览器实测）

```
扩展状态        region 省市区选择器 1.0.0 已启动 ✅
字段注册        region 类型存在，字段类指向 RegionField ✅
Form 可用       $form->region('area') → RegionField ✅
未注册方法     抛 BadMethodCallException + 可用类型列表 ✅
编译产物        area type=region props={level:3} ✅
三级联动        选「广东省」→ 市出现广州/深圳 ✅
               选「深圳市」→ 区出现罗湖/福田/南山/宝安 ✅
两级模式        ->cityLevel() 只渲染两个下拉 ✅
JS 错误         无 ✅
```

### 修复的一个真实 bug

**新增弹窗打开时报错**：`TypeError: Cannot read properties of undefined (reading 'province')`

原因：插件字段的级联状态只在 `edit()` 里初始化，
**新增**时模板直接访问 `regionForm[f.name].province` → undefined。

修复：改为 `ensureRegion(f.name)` 惰性初始化 + 新增按钮走 `openCreate()` 预置状态。

> 这个 bug 只有**真实点击「新增」**才会暴露 ——
> 又一次印证：声明能编译 ≠ 功能可用。

### 结论

插件机制**可用**，但需要框架提供两个扩展点（字段类型注册 + Form 方法分发）。
这两个缺口在写真实插件之前完全不知道存在。

## 补记：电商场景报告揭示的 4 个框架问题（已修复）

第一件事的 AI 交付后提交了详细报告，独立复现确认**全部属实**，其中 2 个高危。

### 高危 1：关联列 + searchable 必然 500，而校验器给绿灯

**复现**：
```
可搜索列: order_no, product.name
❌ 500: no such column: product.name
✅ 校验器: all_satisfied = true
```

**根因**：`applySearch()` 直接 `orWhere('product.name', ...)`，
SQL 把它当列名。且会**连带拖垮同一查询里的其它条件**（`order_no` 也搜不了）。

**修复**：关联路径走 `whereHas()`。

**更重要的修复**：校验器增加**运行时探测** ——
对声明为可搜索的关联列，实际跑一次查询验证不报错。

```php
// 新增输出
✅ 可搜索: order_no, product.name — 已满足
✅ 关联列搜索: product.name — 已实测可执行（未报错）
```

### 高危 2：导出与界面不一致（文档承诺落空）

**复现**（修复前 vs 修复后）：

| 列 | 修复前 | 修复后 |
|---|---|---|
| buyer_id | `2` | 演示用户2 |
| amount | `11998.00` | ¥11998.00 |
| status | `paid` | 已付款 |
| payment_method | `alipay` | 支付宝 |

文档承诺「导出内容与界面一致」，**实际只有行数一致**。
对以导出交付运营的后台是硬伤 —— 运营看到的是英文状态码。

**修复**：`Exporter::value()` 套用列的 formatter（map/bool/money/datetime）。

### 中危 3：Repository 替换点对 HTTP 不生效

**根因**：`ResourceController::repository()` 硬编码 `new EloquentRepository()`，
从未从容器解析契约 —— 文档承诺的 `$this->app->bind(...)` 在 HTTP 路径下无效。

**修复**：优先从容器解析 `Contracts\Repository`；非 EloquentRepository 实现
通过 `EloquentRepository::fromContract()` 适配。

**验证**：用落盘探针确认 —— 绑定自定义实现后，HTTP 请求真的调用了它。

### 说明 4：会话期间框架被修改（不是缺陷）

AI 报告"框架在会话进行中被修改" —— 这是**父 Agent 在同一时间修复真实场景
暴露的短板**（关联列、条件高亮）。确实会导致 AI 早期探测结论失效。

**教训**：不宜在 AI 实测进行中修改框架。

### AI 自己犯的 5 个错（其中 1 个极有价值）

AI 为消掉校验器的「❌ 缺少 product_id」，给外键 `product_id` 加了 `searchable()`，
校验器立刻显示"全部满足" —— 但客户要的是**按商品名搜索**，
实测 `keyword=iPhone` 返回 0 条。

> **校验器只验列名在不在，不验搜的是不是业务字段。**

这条促使我们加了运行时探测（见高危 1 的修复）——
虽然仍无法判断"业务语义是否正确"（那是人的判断），
但至少能挡掉"必然 500 却拿绿灯"这类假阳性。

## 第四件：CRM 真实场景验证（v1.6.0）

完整记录见 [CRM真实场景验证](./CRM真实场景验证.md)。

**一句话结论**：v1.6.0 的六项基座能力在真实 CRM 下站得住，
但挖出 **4 个「界面看着正常、测试全绿」的缺陷**并当场修复。

| 覆盖率口径 | 结果 |
|---|---|
| 单表 CRUD + 关联 + 展示 + 导出（19 项） | 19 / 19 = **100%** |
| 加上跨表聚合 / 定时 / 报表类需求（22 项） | 19 / 22 = **86.4%**（未达 90% 目标） |

修的四个缺陷：

1. **条件高亮从来没有过视觉效果** —— JS 类名与 CSS 对不上 +
   CSS 特异度被表格规则覆盖 + 资源缓存导致改了看不到，三层叠加
2. **`daterange` 没有列契约** —— 前端硬编码 `{name}_start`，真实列名无法声明
3. **数值字段留空 → NOT NULL 违约** —— 空串经 `ConvertEmptyStringsToNull` 变 null
4. **`->dict()` 让 CSV 导出退回英文** —— `badge()` 覆盖了 `map` formatter

> 教训：**「加了一个能力」不等于「这个能力能用」。**
> `dangerWhen()` 是第一件验证加的能力，到第三件才发现从未生效 ——
> 因为当时的验收方式是「类名加上了」，而不是「颜色变了」。
> 验收标准必须盯着**用户可感知的结果**。
