# 竞品基座功能调研与取舍建议

> 调研日期：2026-10-10 · 调研对象：12 个后台框架/模板
> 方法：**全部读一手材料**（README / 官方文档 / 源码树 / 建表 SQL / 官方功能对比页），不凭记忆
> 目的：回答"哪些基座功能该进 Aimanong，哪些不该"

---

## 〇、一句话结论

**竞品覆盖率不是决策依据，只是输入。** 对 Aimanong 而言真正的决策依据是三条：

1. 这个功能**能不能被一份 PHP 声明表达**（而不是后台手点出来）
2. 这个功能**能不能进"单一数据源"三处**（Capabilities / SearchDocs / DocsCommand）
3. 加了它，**AI 写业务的正确率是升还是降**

按这三条筛完，结论会和"照抄若依"很不一样——**该抄的抄，该砍的砍，还有两个要反着做**。

# 第三部分：关键判断 —— 基座准入四准则

覆盖率只是输入。真正的准入测试是这四条：

| # | 准则 | 为什么 | 反例 |
|---|---|---|---|
| **C1** | **血缘修正后的覆盖率 ≥ 5/8** | 过滤同源放大 | 岗位(3/8)、字典(3/8) 单靠 C1 都进不来 |
| **C2** | **能一份 PHP 声明表达** | 声明式是本框架的根。要靠后台手点的功能 = 不可复现 | 可视化表单设计器 ❌ |
| **C3** | **能进单一数据源三处** | Capabilities / SearchDocs / DocsCommand 少一处就是分叉 | 拖拽设计器产出的 JSON ❌ |
| **C4** | **提升 AI 一次成功率** | 北极星指标 | 数据权限无法自动验证 → 反而制造"假绿灯" ❌ |

**C1 决定"要不要"，C2–C4 决定"要也怎么做"。**

## 3.0 一个额外发现：菜单有两种流派，我们选对了

调研中一个**没被预料到、但对本框架极为重要**的发现：竞品在"菜单从哪来"上分成两派，且**分界线正好是"面向人"还是"面向代码"**。

| 流派 | 谁 | 菜单存哪 | 改菜单要做什么 |
|---|---|---|---|
| **DB 驱动**（后台点） | 若依、Jeecg、yudao、Pig、Lamp、**dcat** | 数据库表<br>（`sys_menu` / `admin_menu`） | 登录后台 → 菜单管理 → 新增一行 |
| **代码声明**（写代码） | **Filament**、**Nova**、Django | PHP 代码<br>（`navigation()` / `Nova::mainMenu()` / `ModelAdmin`） | 改代码 → 部署 |

**证据**：
- dcat：`AdminTablesSeeder` 里 `Menu::insert([...])` 写死 5 项，之后全靠 `auth/menu` 页面增删
- Nova 文档原文：`Nova allows you to define your own main menu via the Nova::mainMenu method`
- Filament：菜单由 Resource/Page 类的 `navigation` 属性推导，**源码树中不存在菜单表**

**为什么这对我们重要**：

国产 Java 阵营（若依、Jeecg、yudao、Pig、Lamp）**全部**是 DB 驱动；PHP/Python 阵营（Filament、Nova、Django）**全部**是代码声明。dcat 是唯一例外——它是 Laravel 生态里唯一的 DB 派。

而 Aimanong 选了**第三条路、也是最好的一条**：`Resource::menu()` **声明式** ——
既像代码声明派一样**能 git diff、能被 AI 读到**，又像 DB 派一样**零额外配置**（注册 Resource 就有菜单，不实现也有默认菜单）。

**结论**：**菜单系统的设计已经是正确形态，不要在"基座功能"的名义下把它改回 DB 驱动**（例如新增"菜单管理"页面去覆盖声明）。

> ⚠️ **这条要明确写进设计约束**：将来若有人提议"加一个可视化菜单管理页"，答案是**不**——
> 那会让菜单变成"代码里一份 + 数据库里一份"，正是 `SingleSourceOfTruthTest` 防的那类事故。
> 菜单的调整方式是**改 `menu()` 声明**，不是点后台。

## 3.1 判定的重点：三个反直觉结论

### 结论一：数据字典 **覆盖率低（3/8），但必须做** —— 因为 C4

字典在国产 Java 阵营有、在 PHP/Python 阵营几乎没有（dcat/Filament/Nova/Django 全无）。
按 C1 它进不了基座。

**但**，对照 Aimanong 现状看（`llms.txt` 铁律第 5 条）：

> **枚举优先**：状态类字段用 PHP Enum + `->options(Enum::cases())`

问题是：`options()` 是**每个 Resource 各写各的**。同一个"订单状态"在列表筛选、表单下拉、导出文案里要写三遍，AI 每次都可能抄错一个值。

**字典的价值不是"功能"，是"把散落的枚举收束成可自省的一等公民"**：

```php
// 之前：AI 要自己找到 OrderStatus 枚举，还要猜用例
$grid->column('status')->using(OrderStatus::class);

// 之后：AI 可以从 /__ai/dict 查到有哪些值，直接引用
$grid->column('status', '状态')->dict('order_status');
```

**这是 C4 直接命中的**：AI 少猜一次，正确率就升一次。

> ⚠️ **但这里有个必须正面回答的设计风险**：加了 DB 字典，就有了**两个枚举数据源**（PHP Enum 与 dict 表）——**这直接违反"单一数据源"原则**。

**本报告的解法（见 §3.2 字典条目）**：不是二选一，而是**按"谁来改"划界**，并在 `ai:verify` 里**主动检测同一个字段同时用了两种**。

### 结论二：可视化表单设计器 **覆盖率 3/9，明确不做** —— 因为 C2+C3

若依、Jeecg、yudao 都有"拖拽式表单设计器"。直觉上"别人都有我们也要有"。

**但它与 C2/C3 直接冲突**：
- 拖拽的产物是**数据库里的一段 JSON**，不是代码
- AI **读不到**（不在 Resource 声明里）、**diff 不了**、**验证不了**
- 它会让"单一数据源"裂开成"代码里一份 + 数据库里一份"

**关键区分**（这个区分很重要，别一刀切）：

| | 产物 | 判定 |
|---|---|---|
| dcat 的 `admin:scaffold`、Filament 的 `make:filament-resource`、我们的 `scaffold_resource` | **PHP 代码** | ✅ 可以 —— 代码可 review、可 diff、可 verify |
| 若依「表单构建」、Jeecg「Online 表单」、yudao「表单构建」 | **数据库 JSON 配置** | ❌ 不可以 —— 与自省原则冲突 |

**所以 Aimanong 的答案是：代码生成器 ✅（已有，继续加强），可视化设计器 ❌（永不做）。**

### 结论三：数据权限 **覆盖率 3/9 且全是付费项，不做预置策略** —— 因为 C4

三个证据咬合：
1. **Pig**：数据权限被列入"商业版扩展模块"，从开源版**移除**
2. **Lamp**：官方对比页明确 `数据权限 ❌开源版 / ✅赞助版`
3. **yudao**：数据权限是角色配置的一部分，但依赖部门树（4/9 才有的东西）

**更关键的是 C4**：Aimanong 的 `Capabilities::cannotVerify()` 里**已经诚实地写了**：

> `行级权限`：「A 只能看自己创建的数据」这类需求框架无法验证，也不提供官方拦截点，必须自己写并测试。

**如果我们加了"数据权限"但 AI 不能验证它，就会制造最危险的情况**——`validate_declaration` 返回"全部满足"，而实际越权。这正是你们在多租户场景验证中已经吃过一次的亏（`cannotVerify` 注释原文："`validate_declaration`（含 requirements）全绿的同时…"）。

**所以：保留 `ScopeHooks` 作为可自省钩子，只写文档配方（本部门/本人两段示例代码），不提供框架级预置策略。**

| **声明式实现** | 全局中间件默认开启，Resource 可覆盖：<br>`public static function audit(): array { return ['except' => ['export'], 'snapshot' => true]; }`<br>`snapshot => true` 时记录**字段级 before/after diff**（学 Jeecg 第 41 条） |
| **AI 自省** | ① Capabilities 新增 `audit` 键，列出**当前哪些 Resource 开了审计、排除了哪些 action** —— 让 AI 知道"我这次改动会不会被记录"<br>② SearchDocs 加「审计日志」章节<br>③ DocsCommand 生成 `docs/api/audit.md`<br>④ **MCP 新增 `query_audit_log`**（按 uri/target_id/时间范围查），这是把"审计"从人看的报表变成 **AI 可读的调试接口** |
| **工作量** | 1 表 · 1 Resource · 1 中间件 · 1 MCP tool |

#### P0-3 · 数据字典（**必须做，但做法与竞品不同**）

| 项 | 内容 |
|---|---|
| **覆盖度** | **3/8 独立血统（37%）** —— 若依族 + Jeecg + Lamp；**PHP/Python 阵营全军覆没** |
| **为什么仍必做** | **C4 命中**。现在 `->options()` 散落在每个 Resource，AI 每次都要重新找枚举、重新猜用例。字典把枚举变成**一处定义、处处引用、可 API 自省**的一等公民 |
| **⚠️ 必须正面解决的设计冲突** | 加 DB 字典 = **两个枚举数据源** = 违反单一数据源。竞品没这个问题（它们本来就没有 PHP Enum） |
| **✅ 解法：按"谁来改"划界** | ① **开发期固定** → 用 PHP Enum + `->options(Enum::cases())`（**保持现状**，不迁移）<br>② **运营期可变**（行业/等级/标签类）→ 用 `->dict('code')` 走 DB<br>③ **`ai:verify` 新增校验规则**：同一字段同时声明 `options()` 与 `dict()` → **报错**，并给出二选一建议。**把"双数据源"从隐患变成编译期错误** |
| **声明式实现** | ```php<br>$grid->column('status','状态')->dict('order_status');<br>$form->select('status')->dict('order_status');<br>$grid->filter()->equal('status')->dict('order_status');<br>```<br>2 表（`admin_dict_types` / `admin_dict_items`）+ 1 Resource（字典管理页） |
| **AI 自省** | ① **`GET /__ai/dict`** —— 返回全部字典 code 与值（**这是本功能存在的核心理由**：AI 不查数据库也知道有哪些可选值）<br>② **MCP `list_dictionaries` / `describe_dictionary`**<br>③ Capabilities 新增 `dictionaries` 键<br>④ SearchDocs 加「数据字典」章节<br>⑤ DocsCommand 生成 `docs/api/dict.md`<br>⑥ **`ai:verify` 新增检查**：`dict('x')` 引用了不存在的 code → 报错 + `did_you_mean` |
| **工作量** | 2 表 · 1 Resource · 2 MCP tool · 1 verify 规则 |

# 第五部分：哪些功能"看起来该有，其实是坑"

> 这一节是本报告里我个人认为最有价值的部分。

## 坑 1 · 部门 + 岗位 + 数据权限是**一个三件套**，拆开做哪一个都是坑

**表象**：三个独立功能，覆盖度分别 4/9、4/9、3/9，看起来"各做各的"。

**真相**：它们在若依的设计里是**互相咬合的**——
- `sys_post`（岗位）存在的意义是给"数据权限"提供第二维度
- `sys_dept`（部门）存在的意义是给 `sys_role.data_scope` 提供作用范围（`3：本部门数据权限 4：本部门及以下数据权限`）
- `sys_role_dept` 表专门为"自定数据权限"服务

**所以**：
- 只做部门不做数据权限 → **部门只是一个树形表**，价值接近零（用户完全可以自己加个 `dept_id` 字段）
- 做数据权限 → 需要 `ScopeHooks` 预置策略 + 每个 Resource 声明 + **而它无法被自动验证**

**取舍建议**：

```
部门  → 做成 make 命令模板（零框架成本，不挡路）
岗位  → 不做（它是数据权限的附属品）
数据权限 → 只留 ScopeHooks 钩子 + 文档配方，不做预置
```

**判断依据不是"别人有"，而是"我们做的这一半能不能独立成立"。**

## 坑 2 · 数据字典会引入**第二个枚举数据源**，必须在设计时就掐死

这是本次调研中**最危险的一个坑**，也是最容易被忽略的。

**如果直接照抄若依**（`sys_dict_type` + `sys_dict_data` + 后台管理页），结果会是：

```
同一份"订单状态"，两处定义：
  app/Enums/OrderStatus.php     ← 开发写的，AI 能读到（在代码里）
  admin_dict_items 表            ← 运营改的，AI 读不到（在数据库里）
```

而你们的 `SingleSourceOfTruthTest` 的注释已经预言过这类事故：

> 核心问题：**数据源分叉** —— 同一份信息有多个来源，只更新其中一个会导致 AI 拿到过时数据。

**解法（三条一起上）**：

1. **按"谁来改"划界**（写进 `llms.txt` 铁律）
   - 开发期固定 → PHP Enum（**不迁移、不动摇**）
   - 运营期可变 → `dict()`

2. **`ai:verify` 主动检测**：同一字段同时声明 `options()` 和 `dict()` → **编译期报错**
   ```json
   {"error":"DUAL_ENUM_SOURCE","message":"字段 status 同时声明了 options() 与 dict()",
    "hint":"开发期固定用 options(Enum::cases())；运营期可变用 dict('code')",
    "did_you_mean":"移除其中一个"}
   ```

3. **`/__ai/dict` 必须暴露全部值**，让 DB 侧的值也进入 AI 可读范围

**没有这三条，字典就是"用一个新功能换一个数据分叉"。**

## 坑 3 · 通知公告：**没有展示位的通知系统等于没做**

**表象**：3/9 覆盖（若依有 `sys_notice` + `sys_notice_read`），看起来是标准配置。

**真相**：后端建两张表 + 一个管理页只要半天，但**如果 UI 上没有顶栏铃铛**，这个功能就永远没人用。

**证据**：三个前端模板（AdminLTE/Tabler/AntD Pro）**100% 有通知 UI 位**（NoticeIcon / toasts），而**后端框架里只有一半有通知表**——说明**UI 位才是这个功能的真正工作量所在**，不是后端表。

**取舍建议**：**把"顶栏铃铛 UI"作为前置条件**，UI 没排期就不做后端。这和"先做 UI 再做基座"的既有判断一致。

## 坑 4 · 文件上传：**不要一上来做 7 种存储后端**

**表象**：yudao 支持 S3/MinIO/阿里云/腾讯/七牛/本地/FTP/数据库 8 种，看起来是"完整"。

**真相**：那是 5 年积累。而且每种后端都有独立的坑（签名 URL、CDN 回源、跨域、大文件分片）。

**取舍建议**：
- **阶段 A 只做 local + 一个 `StorageDriver` 接口**
- 接口设计对**公开 URL 的生成方式**留出抽象（因为 S3 的预签名 URL 和 local 的路径完全不同）
- `capabilities.upload` 里**必须暴露** "当前 driver + 公开 URL 前缀"——AI 不知道这个就会生成取不到图的前端代码

## 坑 5 · 用户表加 email/phone 唯一索引 + 软删除 = 经典冲突

**表象**：加两个字段而已。

**真相**：`email` 加唯一索引后，用户被软删除 → **邮箱仍被占用**，新用户注册报"邮箱已存在"，排查半天。

**取舍建议**（必须先决定，不是后补）：
```
要么：不做软删除（用户禁用用 enabled 字段，正好我们已有）
要么：唯一索引带 deleted_at（MySQL: UNIQUE(email, deleted_at)）
```
**鉴于 `admin_users` 已经有 `enabled` 字段——建议直接不做软删除。** 这符合"保持薄"的原则。

## 坑 6 · 可视化设计器是**"看起来最该有、实际最该砍"**的一个

**表象**：若依/Jeecg/yudao 三家都有"拖拽表单设计器"，覆盖率 3/9，是国产阵营的标配。

**真相**：它与 Aimanong 的**根本假设冲突**。

| | 拖拽设计器 | Aimanong |
|---|---|---|
| 产物 | 数据库里的 JSON | PHP 声明 |
| AI 能否读到 | ❌ | ✅ |
| 能否 git diff | ❌ | ✅ |
| 能否 `ai:verify` | ❌ | ✅ |
| 用于人 | ✅ 快 | ⚠️ 要写代码 |
| 用于 AI | ❌ | ✅ |

**关键区分**（别一刀切砍掉生成器）：

> **产出"代码"的生成器 → 要；产出"配置"的设计器 → 不要。**
>
> dcat 的 `admin:scaffold` 产出 PHP 类 → 可以<br>
> 若依的「表单构建」产出 JSON → 不可以

**Aimanong 已有 `scaffold_resource`，形态是对的**（表 → PHP 代码）。**不要被"别人有拖拽我们也要有"带偏。**

## 坑 7 · "竞品覆盖度"本身有**血缘偏差**

前面已经算过：`若依 + yudao` 是**同一血统**（yudao README 自述"基于 RuoYi-Vue 修改"）。

**如果不修正，会系统性高估"国产 Java 后台惯例"的普适性**：

| 功能 | 表面 | 修正后 | 差 |
|---|:--:|:--:|:--:|
| 岗位管理 | 4/9 (44%) | **3/8 (37%)** | 掉了 7 个点，"接近半数"变成"少数派" |
| 数据字典 | 4/9 (44%) | **3/8 (37%)** | 同上 |
| 数据权限 | 3/9 (33%) | **2/8 (25%)** | 且 100% 是付费项 |
| 多语言 | 4/9 (44%) | **4/8 (50%)** | 反向：被低估了 |

**另一条隐藏偏差**：**PHP 阵营（dcat / Filament / Nova）对"数据字典"零覆盖，但对"多语言"全覆盖**。这说明这两件事是**技术栈阵营特征**，不是行业共识。

**Aimanong 是 PHP 框架**——照抄 Java 阵营的字典/岗位/部门，其实是在抄一个**不同生态的惯例**。

## 一句话总结

> **竞品告诉你"该有什么"，但只有你的三条原则能告诉你"该怎么做、以及什么不该做"。**
>
> 本报告建议：**做 6 项必做 + 5 项推荐**，其中**数据字典要反着做**（不是加一个功能，而是收束一个已有的分散源）；
> **砍掉 11 项**，其中**可视化设计器、数据权限预置策略、工作流**砍得最坚决——
> 因为它们要么**无法声明式表达**，要么**无法被 AI 验证**，做了反而会稀释"AI 优先"这个唯一卖点。
