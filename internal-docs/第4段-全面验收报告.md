### 验收过程中又抓到一次「发布事故」

第一次真装直接 `Class "Aimanong\Aimanong" not found`。

根因：core 这一轮新增了公开入口与契约，但 `version` 没升（还是 1.0.0）——
发版脚本按版本派生包 tag，于是**同名 tag `v1.0.0` 被 force-update**，
而 **Packagist 不会重新索引一个已存在的 tag**：

```
远端 tag v1.0.0 → f5f1d673（新，含 Aimanong.php）
Packagist 记录  → 50bbc0d3（旧，不含）
```

修法：core 升到 **1.1.0**（它确实新增了公开 API）。

> 这是同一模式在本轮的**第四次**出现：
> **仓内测试用的是本地源码，永远看不到「已发布的包是什么」。**

**补 B 时立刻抓到 3 个真问题**（3 是「静态分析第一次跑就抓到东西」的实证）：

| 问题 | 性质 |
|---|---|
| **`topthink/think-template` 不在包依赖里** | `ThinkView` 用了 `think\Template`，但 `composer.json` 没 require 它 —— 用户单独装 `aimanong/thinkphp` 时渲染视图**必然致命**。demo 是因为自己的 composer.json 里手加了才没暴露 |
| **`think\Middleware::getGlobal()` 根本不存在** | 挂会话中间件前的「是否已存在」探测调了一个不存在的方法 → 异常被吞 → 永远返回 false → 每次 boot 都重复添加 |
| **类型提示写错（`Query` vs `BaseQuery`）** | `query()` 实际返回 `BaseQuery`；`getFields()` 在 `Query` 上 |

第一条与「thinkphp 未发布」是同一类：**测试环境手动补了什么，就掩盖了包缺什么**。

**thinkphp-e2e：105 → 107 项。**

**修复过程中又发现一个真 bug**（原审计没抓到）：

> TP 的路由变量 `:uri` **默认不匹配连字符** —— `/api/readonly-customers`
> 被截成 `/api/readonly`，报「Resource [readonly] 未注册」。
> 一个看起来像「资源没注册」的错，实际是路由把名字切断了。
> 带连字符的资源名在真实项目里很常见（`shop-products`、`order-items`）。
> 已修（显式 pattern），并有断言。

**thinkphp-e2e：87 → 105 项**（新增 18 项 P0 断言）。

## 三、发现的问题

### 🔴 A. `aimanong/thinkphp` 用户装不到（最高优先级）

```
Packagist  aimanong/thinkphp   → ❌ 未收录
GitHub     aimanong-thinkphp   → ❌ 仓库不存在
发布脚本   包列表硬编码 core/laravel/framework/region → 无 thinkphp
```

**这是第 4 段最大的缺口**：3451 行、25 个文件、87 项 e2e 全覆盖的驱动，
**任何用户都无法安装**。能跑通只是因为 `setup-thinkphp-demo.sh` 用了
path 仓库指向 monorepo —— **测试环境掩盖了发布缺口**。

> 这正是这个项目反复出现的模式：**门禁测的是「仓内能不能跑」，
> 而用户的路径是「从 Packagist 装」**。两者不是一回事。

### 🔴 B. ThinkPHP 包没有任何静态分析

```
packages/thinkphp/ 目录内容：composer.json config resources route src
对照 packages/laravel/：    + phpstan.neon phpunit.xml tests/ vendor/

PHPStan 分析路径：src, tests, ../core/src   ← 不含 ../thinkphp/src
Pint 运行目录：    packages/laravel            ← 不含 thinkphp
```

实测把 thinkphp 放进 PHPStan：**343 个错误**（其中大部分是
`topthink/framework` 未安装导致的 `class.notFound`）。

**结论**：3451 行代码**没有过一次静态分析**，代码风格也没有统一过。
它现在能跑，是因为 e2e 覆盖了运行时路径 —— 但类型错误、未定义属性
这类问题门禁完全看不到。

### 🔴 C. 跨框架语义缺口（这是「同一套声明」主张的直接反证）

由审计子代理发现、**主会话逐条复核确认**：

| # | 缺口 | 证据 | 后果 |
|---|---|---|---|
| 1 | **多租户隔离在 TP 上失效** | Laravel `EloquentRepository.php` 4 处 `ScopeHooks`；TP `ThinkDataSource.php` **0 处** | **跨租户数据全量返回** —— 安全问题 |
| 2 | **只读资源在 TP 上可写** | Laravel `assertWritable` 2 处；TP **0 处** | PUT/POST/DELETE 只读资源**真的写库**；而共享的 `OpenApiEmitter` 按 readonly 省略写接口 → **产物说不许写、接口却接受写** |
| 3 | **多对多关联静默丢弃** | TP `[$data] = $this->splitRelationFields(...)` 丢弃第二个返回值（relations）**2 处** | `multiSelect()->relation()` 提交成功但不写中间表、不报错 —— **与 Laravel 注释里记录的那次幽灵能力事故一模一样** |
| 4 | **`requiredOnCreate()` 在新增时不生效** | Laravel 新增时 `array_unshift($list,'required')`；TP 只在**非新增**时 drop require | 新增不带密码 → 无 422 → 撞 NOT NULL → **500**（Laravel 是 422 友好提示） |
| 5 | **权限节点名不一致** | Laravel 查 `{uri}.create`（`ACTIONS` 里有 `create`）；TP 查 `{uri}.store` | 按声明／AI 生成 `{uri}.create` 授权后，TP 新增永远 403；而 `{uri}.store` 在节点集里不存在 |
| 6 | **唯一键冲突直接 500** | Laravel catch `QueryException` → 422 + 字段 + hint；TP 无 try/catch | 重复唯一值 → HTML 500，调用方拿不到是哪个字段 |
| 7 | 自定义管理员模型在 TP 上登录永远失败 | `ThinkGuard` 硬判 `instanceof Administrator` | 配置 `auth.model` 后登录恒返回「账号或密码不正确」 |
| 8 | 字典配置路径不同 | Laravel `aimanong.foundation.dict.*`；TP `aimanong.dict.*` | 同一份声明换框架 → 字典为空 → `->dict()` 抛异常 |
| 9 | 上传默认值/配置路径不同 | 图片白名单 6 vs 5 项；`foundation.upload.*` vs `upload.*` | 两端产物不同；且 **TP 没有 upload 路由** → 产物宣告的端点 404 |
| 10 | 路由前缀键名不同 | `aimanong.route.prefix` vs `aimanong.prefix` | 配置文件不能互换 |
| 11 | 时间字段序列化不同 | Laravel ISO-8601 vs TP `Y-m-d H:i:s` | 同一资源 JSON 形状不同 |
| 12 | 登录状态码/响应体不同 | 限流 422 vs 429；密码错 422 vs 401；**禁用账号 Laravel 静默、TP 明确提示** | **TP 可探测账号是否被禁用**；且响应契约不一致 |
| 13 | 会话未重新生成 | Laravel `regenerate()`+`migrate()`；TP 只 `Session::set` | **会话固定（session fixation）风险** |
| 14 | 限流账号未规范化 | Laravel `mb_strtolower(trim())`；TP 用原始串 | `Admin` / `admin` 是两个计数桶 → **限流可被大小写绕过** |

> **其中 1 / 2 / 13 / 14 是安全问题**，不是「体验差异」。

## 四、为什么会漏掉这些

这次验收发现的**绝大多数问题，都不是「写错了代码」**，而是：

1. **「跑通了」≠「对」** —— TP 的 `/admin` 200、数据 API 200、登录成功，
   全是**真的**。但只读资源被写、多租户隔离失效、多选关联丢失，
   **在 200 的响应里完全看不出来**。
2. **e2e 覆盖了「能被观察到」的路径**，而 ScopeHooks / readonly /
   relation sync 这三个，**要专门构造场景才会触发**，e2e 没构造。
3. **门禁测的是仓内路径，用户的路径是从 Packagist 装** ——
   thinkphp 未发布这件事，87 项 e2e 一项都测不到。
4. **两套实现没有「对拍」机制** —— 我逐个核实了「TP 的测试通过」，
   但从未系统性地把两边的**同一个输入**跑一遍比较输出。
   跨框架审计做了一次，立刻就找出 14 条。

> 一句话：**我一直在验证「TP 能不能跑」，而没有验证「TP 和 Laravel 一不一样」。**
> 而第 4 段的核心主张恰恰是后者。
